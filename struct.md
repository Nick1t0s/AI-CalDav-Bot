# AI-CalDav-Bot — полная и подробная структура проекта

Этот документ объясняет, как устроен проект **AI-CalDav-Bot**, начиная с нуля.
Он написан так, чтобы его мог прочитать человек, который никогда не видел ни
Telegram-ботов, ни aiogram, ни CalDAV, ни iCalendar, ни нейросетей. Поэтому
сначала идёт «школьная» часть (что такое каждый кирпичик), а потом — построчный
разбор кода и путь каждого сообщения.

Ориентир: код в этом репозитории — это «правда». Все имена функций, файлов,
переменных и строки взяты из реального кода на момент написания документа.

# Часть 1. Школа: базовые понятия

## 1.1. Что такое Telegram-бот

Telegram — это мессенджер. У него есть официальный API (интерфейс, по которому
разные программы могут общаться с серверами Telegram). Бот — это программа,
которая подключена к этому API и отвечает на сообщения пользователей так же,
как отвечал бы человек.

Пользователь пишет боту сообщение. Сервер Telegram получает его и должен как-то
отдать программе-боту. Есть два механизма:

1. **Webhook** — программа-бот заранее сообщает Telegram: «мой сервер живёт по
   адресу `https://...`; все события отправляй мне на этот адрес». Telegram
   тогда сам «стучится» к программе при каждом событии.
2. **Long polling** — программа-бот сама периодически спрашивает сервер: «есть
   что-нибудь новое?» Сервер отвечает списком **update** (событий) или ждёт,
   пока что-нибудь появится. Этот вариант проще — не нужен публичный IP.

Этот проект использует **long polling** (см. `main.py`).

Объект, который Telegram присылает боту, называется **Update**. Внутри Update
могут быть разные вещи:

- **Message** — новое сообщение (текст, фото, документ, нажатие на команду);
- **CallbackQuery** — нажатие на инлайн-кнопку под сообщением;
- и многое другое (новый участник чата, редактирование сообщения и т.д.).

В этом проекте интересны только два вида: текстовое сообщение (`Message`) и
нажатие на кнопку (`CallbackQuery`).

## 1.2. Что такое aiogram 3

**aiogram** — это Python-библиотека, «обёртка» над Telegram Bot API. Она берёт на
себя всю рутину: HTTP-запросы к API, разбор JSON, поддержку длинного опроса
(long polling), типы данных (Message, CallbackQuery, кнопки) и так далее.

Ключевые понятия aiogram, которые нужны для чтения этого проекта:

- **`Bot`** — объект, который хранит токен бота и умеет отправлять запросы к
  API (отправить сообщение, отредактировать сообщение, показать индикатор
  «печатает»). Создаётся в `main.py`.
- **`Dispatcher`** — «центральный диспетчер»: он получает каждый Update и
  решает, кто его должен обработать. В проект включаются обработчики через
  `dp.include_router(router)`.
- **`Router`** — «папка» обработчиков. В `handlers.py` создан один
  `router = Router()`, и на нём вешаются все функции-обработчики через
  декораторы.
- **`@router.message(...)`** — регистрирует функцию-обработчик для входящих
  сообщений. В скобках указывается **фильтр** — условие, при котором функция
  сработает. Например `F.text` — «сообщение содержит текст».
- **`@router.callback_query(...)`** — регистрирует обработчик нажатий на
  инлайн-кнопки. `F.data.startswith("op:")` — «callback содержит данные,
  начинающиеся с `op:`» (кнопки подтверждения плана).
- **`Message`** — объект сообщения: `message.text` (текст), `message.chat`
  (чат), `message.from_user` (кто написал), `message.bot` (бот).
  `await message.answer(text)` — ответить сообщением.
- **`CallbackQuery`** — объект нажатия на кнопку: `cb.data` (строка,
  зашитая в кнопку), `cb.from_user`, `cb.message` (сообщение, под которым
  кнопка). `await cb.answer(...)` — «погасить» нажатие (показать/не показать
  уведомление). `cb.message.edit_text(...)` — изменить текст сообщения под
  кнопкой.
- **Инлайн-кнопки** — кнопки, которые лежат под сообщением. Каждая кнопка —
  `InlineKeyboardButton(text=..., callback_data=...)`. Все кнопки собраны в
  `InlineKeyboardMarkup` (сетку из рядов). Когда пользователь жмёт кнопку,
  Telegram присылает боту `CallbackQuery`, а `callback_data` — это «код», по
  которому бот понимает, что делать.
- **`ChatAction`** — индикатор «печатает»/«отправляет…». `TYPING` показывает
  пользователю «бот печатает».
- **ParseMode** — формат текста: `HTML` значит, что в тексте можно
  использовать HTML-теги (`<b>`, `<i>`, `<a>`) и они отрисуются красиво.
  В `main.py` включается глобально.

Важная деталь: aiogram — **асинхронный**. Все функции-обработчики — `async
def`, и в них нельзя делать долгие «блокирующие» операции (например, ждать
ответ нейросети секунды напролёт), иначе весь бот «зависнет». Поэтому в этом
проекте тяжёлая работа выносится в отдельный поток через `asyncio.to_thread(...)`
(см. раздел 8).

## 1.3. Что такое CalDAV (и почему Яндекс)

**CalDAV** — это стандартный протокол для доступа к календарям по сети. Он
основан на HTTP и называется «CalDAV», потому что использует идеи **WebDAV**
(работа с документами на сервере по HTTP: создание, чтение, редактирование,
удаление).

Яндекс Календарь предоставляет свой сервер CalDAV по адресу
`https://caldav.yandex.ru`. Это значит, что любую программу, умеющую
разговаривать по CalDAV, можно подключить к Яндекс-календарю: читать события,
создавать их, менять, удалять — точно так же, как через веб-интерфейс.

Понятия CalDAV, нужные для проекта:

- **URL сервера** — базовый адрес, например `https://caldav.yandex.ru`.
- **Principal** — «личность» пользователя. У Яндекса principal пользователя
  описывает его календари. В терминах кода: `client.principal()` возвращает
  объект principal.
- **Calendar** — конкретный календарь пользователя. У одного пользователя
  может быть несколько календарей (личный, рабочий, праздники и т.д.).
- **Событие (Event)** — запись в календаре. На сервере каждое событие — это
  отдельный «ресурс» (файл) с **URL**. Через этот URL его можно перезаписать
  или удалить.

Как логин в Яндекс: логин — полная почта (`you@yandex.ru`), а пароль — не
обычный, а **App password** (специальный пароль для приложений). Его создают в
настройках Яндекса (id.yandex.ru/security/app-passwords), тип «Календарь».

В проекте с CalDAV работает модуль `caldav_service.py` с помощью библиотеки
**`caldav`** (Python-клиент протокола) и **`icalendar`** (парсер формата iCal,
см. следующий раздел).

## 1.4. Что такое iCalendar (и библиотека icalendar)

**iCalendar** (часто называют просто **iCal**) — это текстовый формат для
хранения календарных данных. Им обмениваются календари: сервер CalDAV хранит
события именно в этом формате. Файл формата `.ics` — это текст.

Основной компонент формата — **VEVENT**: блок описания одного события. Пример:

```
BEGIN:VEVENT
UID:8b5f...@yandex.ru
DTSTAMP:20260101T000000Z
DTSTART:20260108T130000Z
DTEND:20260108T140000Z
SUMMARY:Встреча с Аней
LOCATION:Кофейня
RRULE:FREQ=WEEKLY;BYDAY=MO
END:VEVENT
```

Свойства (поля), которые важны для этого проекта:

- **UID** — уникальный идентификатор события. По нему календари понимают, что
  это одно и то же событие.
- **DTSTART** — начало. **DTEND** — конец. Могут быть с временем (datetime) или
  только датой (`20260108` = весь день).
- **DTSTAMP** — когда запись была создана/изменена.
- **SUMMARY** — название. **LOCATION** — место. **DESCRIPTION** — описание.
- **RRULE** — правило повтора (recurrence rule). Например
  `FREQ=WEEKLY;BYDAY=MO,TH` значит «каждую неделю по понедельникам и
  четвергам». Бывают `FREQ=DAILY/WEEKLY/MONTHLY/YEARLY`, `INTERVAL` (каждые N
  периодов), `UNTIL` (до даты), `COUNT` (количество раз), `BYDAY`, `BYMONTHDAY`.
- **EXDATE** — список дат, которые **исключены** из серии. Например, серия «каждый
  понедельник», но 10 августа занятие отменили → 10.08 попадает в EXDATE.
- **RDATE** — список **дополнительных** (внеплановых) вхождений серии. Например,
  «каждый понедельник, плюс один раз во вторник 15-го».
- **RECURRENCE-ID** — «я — отдельное, особое вхождение серии» (см. ниже
  «отвязанные вхождения»).
- **VALARM** — напоминание. Внутри него `TRIGGER:-PT60M` = «за 60 минут до
  начала», `ACTION:DISPLAY`.
- **SEQUENCE** — счётчик изменений события (для синхронизации).

Как обрабатывается повторяющееся событие:

- На сервере (в «мастер-событии») хранится ОДНА запись с `RRULE`.
- Но пользователь в календаре видит «каждое вхождение» — каждый понедельник
  отдельно. Вхождения **вычисляются** из правила.
- Python-библиотека **`recurring_ical_events`** делает это вычисление: берёт
  правило повтора, EXDATE, RDATE и порождает список конкретных дат.
- **Исключить одно вхождение из серии** = добавить дату в `EXDATE` мастера.
- **Изменить одно вхождение из серии** = добавить дату в `EXDATE` **и** создать
  отдельное «отвязанное» событие (`RECURRENCE-ID`), которое перекрывает
  обычное вхождение на эту дату.

Важная тонкость из формата: для события «весь день» даты хранятся **без**
часового пояса (просто `20260108`), а для событий по времени — **с** временем
и поясом (в проекте — в UTC). Код всё время проверяет `_is_all_day(...)`,
чтобы правильно обработать оба случая.

## 1.5. Что такое нейросеть и LLM

**LLM** (Large Language Model) — большая языковая модель. Это нейросеть,
обученная на огромном количестве текстов. Грубо говоря, её работа — предсказывать
**следующий токен**: получив кусок текста, она по вероятности выбирает
следующее слово (точнее, токен — кусочек слова), потом ещё одно, и так далее,
пока не получится ответ.

На практике LLM читает на вход **промпт** — инструкцию с контекстом — и
возвращает текст-ответ. Качество ответа зависит и от инструкции, и от данных,
которые мы в неё подставили.

Параметры вызова модели, которые использует проект:

- **`temperature`** — насколько «творческой» быть модели. `temperature=0`
  означает максимально детерминированный (однообразный) выбор, почти без
  случайности. Для инструментальной работы это правильно: мы хотим, чтобы на
  одинаковый ввод был одинаковый вывод.
- **`model`** — какая модель используется (например `gpt-4o-mini`).
- **`messages`** — список сообщений диалога (роли `system`, `user`,
  `assistant`, `tool`).
- **`tools`** — объявления инструментов (см. следующий раздел).
- **`tool_choice`** — политика вызова инструментов. `"auto"` — модель сама
  решает, вызвать ли инструмент (или ответить текстом).

Проект использует не «официальный» только OpenAI, а **любой OpenAI-совместимый
API**: указывается `OPENAI_BASE_URL` (OpenAI, OpenRouter, локальный vLLM) и
`OPENAI_MODEL`. Код ходит в эндпоинт `/chat/completions`.

## 1.6. Function calling: инструменты и «скиллы» нейросети

Сама по себе нейросеть не может ничего сделать руками: она только возвращает
текст. Механизм **function calling** (в народе «tools», «инструменты», а в
терминах агентов — «skills») даёт модели способ «попросить код что-то сделать».

Как это работает:

1. Программа объявляет инструменты: «у меня есть функция `get_period` с
   параметрами `date_from`, `date_to`». Это называется **схема инструмента**
   (JSON Schema). Модель получает эти схемы в запросе.
2. Модель читает запрос пользователя и понимает: «чтобы ответить, мне нужен
   список событий». В своём ответе она вместо обычного текста пишет:
   **`tool_calls`** — «вызовите функцию `get_period` с аргументами `{}`».
   Важно: модель **не выполняет** функцию сама. Она только «заказывает» вызов.
3. **Программа (наш код)** выполняет функцию реально: ходит в CalDAV, читает
   календарь, формирует текст-результат.
4. Программа кладёт результат обратно в историю диалога как сообщение роли
   **`tool`** (привязывая его к конкретному `tool_call_id`).
5. Программа снова вызывает модель уже с этим результатом. Модель видит данные
   и либо вызывает ещё инструменты, либо завершает ответ.

Весь цикл «модель → вызов инструмента → результат → модель» называется
**агентным циклом**, а программа, которая его крутит, — **агентом**.

В этом проекте ровно 4 инструмента (подробно — в разделе про `agent.py`):

| Имя | Роль |
|---|---|
| `get_period` | Прочитать календарь за период (только чтение, выполняется сразу). |
| `reg_list` | Зарегистрировать список изменений (создать/удалить/исключить вхождение) в план. |
| `ask_user` | Задать пользователю вопрос с кнопками-вариантами. |
| `done` | Завершить ход: финальный ответ (+накопленный план). |

Отличие «инструмента» от «навыка» здесь терминологическое: в этом проекте это
одно и то же — четыре функции, которые умеет вызывать нейросеть. (В некоторых
фреймворках «скиллами» называют крупные готовые блоки возможностей, но здесь
такого разделения нет.)

## 1.7. Агентная архитектура и главный принцип безопасности

Классический бот устроен так: «услышал команду → выполнил команду». Здесь
другая схема — **агентная**: нейросеть сама разбирает естественный язык,
сама решает, что нужно сделать, и сама планирует шаги. Но она **не трогает
календарь**.

Главный принцип проекта, повторённый в коде и в системном промпте:

> **LLM планирует, скрипт исполняет.**

- Нейросеть может только **читать** календарь (`get_period`) и **накапливать
  план** изменений (`reg_list`).
- Никакие изменения не записываются в календарь в момент, когда их
  «придумала» модель.
- План показывается человеку списком с кнопкой **«✅ Выполнить всё»**.
- Только после нажатия человеком **обычный скрипт** (без ИИ) выполняет
  изменения через CalDAV.

Это защищает от галлюцинаций (модель выдумала несуществующее событие и удалила
его), от «лишних» действий и от случайного удаления: человек всегда видит, что
собирается сделать бот, и подтверждает кнопкой.

## 1.8. Асинхронность и потоки (кратко)

В проекте пересекаются два механизма параллельности:

- **asyncio / event loop** — способ одного процесса обслуживать много
  сетевых операций «одновременно»: пока ждём ответ Telegram API, можем
  заниматься другим. Всё, что связано с aiogram, работает в event loop.
- **Потоки (threads)** — настоящая параллельность на уровне ОС. Долгие
  синхронные операции (нейросеть, CalDAV) выносятся в потоки, чтобы не
  блокировать event loop.

`asyncio.to_thread(fn, args...)` запускает обычную (синхронную) функцию `fn`
в отдельном потоке и возвращает awaitable. Именно так здесь вызываются
`run_agent`, `_perform_plan`, `answer_ask`, `resume_agent`.

Чтобы два сообщения из одного чата не «перемешались», на каждый чат есть
отдельный `threading.RLock` (reentrant lock) — блокировка. Внутри неё обрабатывается
весь ход одного сообщения. (Подробности — раздел 8.)

# Часть 2. Общая картина проекта

## 2.1. Что делает бот

Пользователь пишет боту обычным языком:

- «что у меня завтра»
- «отмени завтрашнее занятие»
- «перенеси занятие на час позже»
- «создай встречу с Аней завтра в 14:00 на час»

Бот:

1. Принимает текст (через aiogram).
2. Запускает агента: нейросеть читает календарь, уточняет вопросы, составляет
   план изменений.
3. Показывает план человеку кнопкой.
4. По подтверждению выполняет план обычным кодом через CalDAV.

## 2.2. Упрощённая схема потока

```
 Telegram (aiogram)
    │  текстовое сообщение
    ▼
 handlers.on_message ──► run_agent(chat_id, text)   [отдельный поток]
                            │
                            ▼
                    CalendarAgent (agent.py)
                    цикл: LLM ⇄ инструменты
                     ├─ get_period  → чтение календаря (caldav_service)
                     ├─ reg_list    → накопление плана в сессии
                     ├─ ask_user    → пауза, вопрос с кнопками
                     └─ done        → финал: текст + план
                            │
                            ▼
                     AgentResult (kind: done / ask / error)
                            │
                            ▼
 handlers._handle_result
    kind="ask"  → вопросы с кнопками (asks.py)
    kind="done" → план + кнопка «✅ Выполнить всё / ❌ Отмена» (confirmation.py)
                            │  нажатие кнопки
                            ▼
 handlers._perform_plan ──► caldav_service (создание/удаление/изменение)
```

## 2.3. Файлы проекта

```
AI-CalDav-Bot/
├── .env                    # секреты и настройки (в gitignore)
├── .env.example            # образец .env с комментариями
├── requirements.txt        # зависимости Python
├── config.py               # чтение .env → константы
├── main.py                 # точка входа: запуск бота
├── handlers.py             # Telegram I/O: обработчики сообщений и кнопок
├── agent.py                # агент: инструменты, чат-цикл, сессии
├── caldav_service.py       # CRUD поверх CalDAV (протокол и iCal)
├── confirmation.py         # реестр планов + кнопка подтверждения
```

# Часть 4. Данные, которые циркулируют между слоями

Прежде чем разбирать код, перечислим «типы-контейнеры», через которые слои
общаются.

## 4.1. `EventData` (`caldav_service.py`)

Описание одного события (или одного вхождения повторяющегося события).
Это центральный объект, который используется везде дальше.

Поля:

| Поле | Тип | Смысл |
|---|---|---|
| `url` | `str` | URL ресурса-владельца на сервере. Для серии все вхождения ссылаются на URL мастера. По нему потом перезагружают мастер для правки/удаления. |
| `uid` | `str` | UID события. |
| `summary` | `str` | Название. |
| `location` | `str` | Место. |
| `description` | `str` | Описание. |
| `start` | `datetime` | Начало (в TZ пользователя). |
| `end` | `datetime` | Конец. |
| `all_day` | `bool` | «Весь день» (тогда даты без времени). |
| `is_recurring` | `bool` | Есть ли `RRULE` у мастер-события. |
| `instance_start` | `datetime` | Для вхождения серии — его дата. Для одиночного события — `None`. |
| `rrule` | `str` | Сырая строка `RRULE` мастера. |
| `series_count` | `int` | Сколько вхождений серии попало в запрошенный период. |
| `series_first` / `series_last` | `datetime` | Первое/последнее вхождение в периоде. |
| `exdates` | `list` | Исключённые даты мастера (`EXDATE`) как локальные `date`. |
| `rdates` | `list` | Внеплановые вхождения (`RDATE`). |
| `alarms` | `list` | Напоминания (минуты до начала). |
| `categories` | `list` | Категории. |
| `status` | `str` | `CONFIRMED` / `TENTATIVE` / `CANCELLED`. |
| `transp` | `str` | `OPAQUE` (занят) / `TRANSPARENT` (свободен). |
| `priority` | `int` | Приоритет 1–9. |
| `link` | `str` | Свойство `URL` (веб-ссылка). |

Свойство `duration` (вычисляемое) = `end - start`.

Важно: для одного и того же мастер-события может быть МНОГО `EventData` — по
одному на каждое вхождение периода. Все они имеют одинаковый `url`, `uid`,
`rrule`, `is_recurring=True`, но разный `start` и `instance_start`.

## 4.2. `PlanAction` (`confirmation.py`)

Одно действие плана. Что именно исполнится, когда пользователь нажмёт
«Выполнить всё».

| Поле | Смысл |
|---|---|
| `kind` | `"create"` / `"delete"` / `"exclude"`. |
| `event` | `EventData`, к которому относится действие (для delete/exclude). |
| `payload` | Словарь параметров для создания (для create). |
| `scope` | Оставлен для совместимости, но **не используется** (операции `update` и `scope=instance/all` убраны). |
| `changes` | Оставлен для совместимости, **не используется** (update убран). |

## 4.3. `BaseOp` / `PlanOp` (`confirmation.py`)

`BaseOp` — просто `user_id` (кому принадлежит операция). `PlanOp` — наследник:
`user_id` + `actions: list[PlanAction]`. Это «пакет ожидающего плана».

## 4.4. `AskQ` (`asks.py`)

«Ожидающий вопрос» агента:

| Поле | Смысл |
|---|---|
| `user_id` | Кому задан вопрос. |
| `tool_call_id` | ID вызова инструмента `ask_user`, к которому нужно «вернуть» ответ. |
| `question` | Текст вопроса. |
| `options` | Список вариантов ответа (будут кнопками). |

## 4.5. `AgentResult` (`agent.py`)

Результат работы агента за один «ход» (одно сообщение пользователя):

| Поле | Смысл |
|---|---|
| `kind` | `"done"` / `"ask"` / `"error"`. |
| `text` | Финальный текст для пользователя (для `done`), либо текст ошибки. |
| `items` | Список коротких пунктов под ответом (для `done`). |
| `plan` | Список `PlanAction`, накопленный за ход. |
| `questions` | Список `{"ask_id", "question", "options"}` для показа в чате (для `ask`). |

## 4.6. Формат сессии агента (`agent.py`, поле `_sessions`)

Для каждого `chat_id` хранится словарь:

```python
{
    "messages":     [...],  # история диалога (роли system не входит)
    "refs":         {...},  # {"e1": EventData | list[EventData], ...}
    "plan":         [...],  # накопленный список PlanAction
    "pending_asks": [...],  # ожидающие вопросы раунда
    "ts":           1723..., # время последней активности (для TTL)
}
```

Подробности каждого поля — в разделе про агента.

# Часть 5. Путь каждого сообщения (главный раздел)

Ниже — четыре «маршрута» сообщения. Для каждого шага указан файл и функция,
чтобы можно было открыть код и идти за текстом.

## 5.1. Путь А: обычное текстовое сообщение пользователя

**Пример:** пользователь написал «удали завтрашнее занятие».

**Шаг 1. Telegram присылает Update → aiogram разбирает его → Dispatcher.**
Long polling в `main.py` (`dp.start_polling(bot)`) получает Update. Dispatcher
смотрит, какой Router подходит.

**Шаг 2. Router → фильтр → обработчик `on_message` (`handlers.py`).**
`@router.message(F.text)` ловит любое сообщение с текстом. Функция:
- `_check_allowed(message)` (`handlers.py:77`) — если `ALLOWED_USER_IDS` пуст,
  пишет «⛔ Доступ запрещён: не настроен ALLOWED_USER_IDS.» и выходит; если
  `message.from_user.id` не в списке — «⛔ Доступ запрещён.» и выход.
- `cleanup_expired()` (из `confirmation.py`) — чистит протухшие планы.
- `cleanup_asks()` (из `asks.py`) — чистит протухшие вопросы.
- `text = message.text.strip()`; пустой текст или начинающийся с `/` — выходим
  (команды `/start`, `/help` обрабатываются отдельными обработчиками).
- `message.bot.send_chat_action(message.chat.id, ChatAction.TYPING)` — показать
  «бот печатает…».
- `_cancel_pending_plan(message.chat.id)` — если в этом чате «висит» ещё не
  подтверждённый план (от предыдущего сообщения), он отменяется: из
  `_PENDING_PLANS` достаётся `op_id` и операция удаляется через `consume`. То
  есть новое сообщение отменяет старый план.
- `run_agent(...)` запускается в отдельном потоке:
  ```python
  result = await asyncio.to_thread(run_agent, message.from_user.id, text)
  ```
  Обратите внимание: ключ сессии агента — **`message.from_user.id`** (ID
  пользователя), а не ID чата.

**Шаг 3. Внутри агента (`agent.py`, `CalendarAgent.run`, строка 619).**
`run_agent(chat_id, user_text)` вызывает `_agent.run(chat_id, user_text)`.

```
run(chat_id, text):
  with self._chat_lock(chat_id):          # блокировка чата
      self._prune()                       # выкинуть сессии старше TTL
      sess = self._session(chat_id)       # взять (или создать) сессию
      unanswered = [вопросы, на которые ещё не ответили]
      if unanswered:
          # этот текст становится ОТВЕТОМ на первый неотвеченный вопрос
          # (это путь 5.3)
          ...
      else:
          sess["messages"].append({"role": "user", "content": text})
          return self._loop(chat_id)      # крутим цикл
```

**Шаг 4. Чат-цикл `_loop` (`agent.py:552`).**
Пока не наберётся `AGENT_MAX_STEPS` шагов:

1. Собирается полный список сообщений для модели:
   ```python
   messages = [{"role": "system", "content": build_system_prompt()}] + sess["messages"]
   ```
   Системный промпт каждый раз собирается заново — с текущей датой, временем и
   TZ (функция `build_system_prompt`, строка 316).
2. Вызов LLM (`_ask`, строка 452): `chat.completions.create(model,
   messages, tools=TOOLS, tool_choice="auto", temperature=0)`. Модель отвечает
   либо списком `tool_calls`, либо обычным текстом.
3. Если `tool_calls` нет — ход неверный. В историю добавляется текст модели,
   план очищается, возвращается `AgentResult(kind="error", text="Не удалось
   завершить ход — агент не вызвал done…")`. (Парадигма «всё есть инструмент»:
   модель обязана закончить `done` или `ask_user`.)
4. Если `tool_calls` есть — сообщение модели сохраняется в историю (вместе с
   tool_calls), и **каждый вызов инструмента обрабатывается по порядку**:
   - `get_period` / `reg_list` / `done` → **выполняются сразу**, результат
     кладётся в историю как сообщение роли `tool` с `tool_call_id` (для `done` —
     ответ «Принято.» и запоминаются финальный текст и `items`);
   - `ask_user` → запоминается **первый** встреченный в пачке (лишние
     игнорируются с предупреждением в лог); пауза происходит после обработки
     всей пачки.
5. После обработки пачки:
   - если был `ask_user` → регистрируется вопрос (через `_register_ask`) и
     возвращается `AgentResult(kind="ask", questions=[один вопрос])` — пауза;
     `done` из той же пачки не исполняется;
   - если был `done` (а `ask_user` не было) → забрать накопленный план из
     сессии, очистить его, вернуть `AgentResult(kind="done", text=..., items=...,
     plan=...)`;
   - если не было ни того ни другого → следующий шаг цикла.

**Шаг 5. Возврат в `handlers._handle_result` (`handlers.py:126`).**
- `kind == "error"` → `await message.answer(f"😕 {esc(result.text)}",
  reply_markup=ReplyKeyboardRemove())` — клавиатура вопроса прячется.
- `kind == "ask"` → для каждого вопроса из `result.questions` (их один) отправляется
  сообщение `❓ {question}` + подсказка «можно написать свой ответ» с
  **reply-клавиатурой** вариантов (`kb_ask(options)`, `KeyboardButton`). Никакого
  плана не показываем — цикл ждёт ответа.
- `kind == "done"` и **план непуст**:
  1. Создаётся `PlanOp(user_id=..., actions=result.plan)`.
  2. `op_id = register(op)` — операция попадает в реестр `confirmation.PENDING`.
  3. `_PENDING_PLANS[chat.id] = op_id` — запоминается «текущий незакрытый план».
  4. Текст = `format_done(text, items)` + пустая строка + `format_plan(plan)`
     (красивый список действий) + кнопка `kb_plan_confirm(op_id)`.
  5. Всё это отправляется одним сообщением.
- `kind == "done"` и **план пуст** → `format_done(text, items)` с
  `ReplyKeyboardRemove()` (клавиатура вопроса прячется).

**Шаг 6. Пользователь видит план и жмёт кнопку.** Дальше — путь 5.4.

## 5.2. Путь B: ответ на вопрос агента кнопкой (reply-клавиатура)

**Пример:** агент спросил «Удалить одно вхождение или всю серию?» и прислал
reply-клавиатуру с кнопками «Это вхождение» / «Всю серию».

Reply-клавиатура (`KeyboardButton`) — это обычные кнопки над полем ввода.
Нажатие на такую кнопку **отправляет её текст как обычное сообщение** —
никаких `CallbackQuery` и обработчика `ask:…` больше нет. Поэтому путь B
фактически совпадает с путём C: текст кнопки приходит в `on_message`
(`handlers.py`), и `run_agent` трактует его как ответ на ожидающий вопрос.

```
on_message(text="Это вхождение")
  → run_agent(user_id, "Это вхождение")
  → run(): есть unanswered → подставить текст как результат ask_user
  → _loop() продолжается → ... → done
```

Клавиатура остаётся открытой, пока ход не закончится `done`/`error` — тогда
`_handle_result` отправляет финальное сообщение с `ReplyKeyboardRemove()`,
и кнопки исчезают. Пользователь также может игнорировать кнопки и написать
свой ответ — это путь C.

## 5.3. Путь C: пользователь отвечает текстом на вопрос агента

Если во время паузы (есть неотвеченные вопросы) пользователь просто напишет
текст — этот текст **не трактуется как новый запрос**, а становится ответом на
первый неотвеченный вопрос.

Это происходит в `run()` (`agent.py:619`): проверяется `unanswered`, и если он
непуст:

1. `q = unanswered[0]`.
2. `consume_ask_op(q["ask_id"])` — вынуть вопрос из реестра `asks.py`.
3. `_append_tool_response(chat_id, q["tool_call_id"], user_text)` — текст
   становится результатом инструмента.
4. `q["answered"] = True`.
5. Если остались другие неотвеченные → `AgentResult(kind="ask")` (ждём дальше).
6. Иначе `sess["pending_asks"] = []` и `_loop(chat_id)` — цикл продолжается.

## 5.4. Путь D: нажатие на кнопку плана (`op:…`)

**Шаг 1.** `CallbackQuery` с `data = "op:<op_id>:<action>"`, где `<action>` —
`plan_confirm` или `cancel`. Обработчик `on_callback` (`handlers.py:188`).

**Шаг 2. Проверки:**
- `cleanup_expired()` — чистим протухшие операции.
- разбор `op_id`, `action`.
- `op = get(op_id)`; если нет — «Операция устарела, попробуйте ещё раз» (alert).
- если `cb.from_user.id != op.user_id` — «Это не ваша операция.» (alert).

**Шаг 3a. `action == "cancel"`:**
- `consume(op_id)` — операция удалена из реестра;
- `_PENDING_PLANS.pop(cb.message.chat.id, None)`;
- `_safe_edit(cb.message, "❌ Отменено.")` — текст плана заменяется.

**Шаг 3b. `action == "plan_confirm"`:**
- `op = consume(op_id)` — операция **забирается** (одноразовая);
- `_PENDING_PLANS.pop(...)`;
- `results = await asyncio.to_thread(_perform_plan, op)` — исполнение в потоке;
- `text = "\n".join(results)` — строки результатов;
- `append_assistant_text(cb.from_user.id, text)` — результат дописывается в
  историю агента, чтобы следующие сообщения «знали» о сделанном;
- `_safe_edit(cb.message, text)` — сообщение плана заменяется результатом.

**Шаг 4. Исполнение плана (скрипт, не ИИ) — `_perform_plan` / `_perform_action`
(`handlers.py:229`):**
Для каждого действия `_perform_action`:
- `create` → `_run_create_action(action.payload)` → `create_event(...)` и строка
  «✅ Создано: «…» (дата, ЧЧ:ММ) [🔁 …]».
- `delete` → `_run_delete_action(action)` → `delete_event(ev)` — удаляется весь
  ресурс (одиночное событие или вся серия целиком).
- `exclude` → `_run_exclude_action(action)` → `exclude_occurrence(ev)` — в мастер
  серии добавляется `EXDATE` (исключается одно вхождение).

Если какое-то действие упало — оно не роняет остальные: `_perform_plan`
оборачивает каждое в try/except и добавляет строку «❌ Ошибка: …».

## 5.5. Путь E: команды `/start` и `/help`

`@router.message(CommandStart())` → `cmd_start` (`handlers.py:90`):
- `_check_allowed` — та же проверка доступа;
- ответ — текст `INTRO` (что умеет бот + примеры запросов).

`@router.message(Command("help"))` → `cmd_help` — то же самое.

Обратите внимание: команды не попадают в агента. Хотя `@router.message(F.text)`
технически ловит и их, внутри `on_message` есть проверка `text.startswith("/")`
→ возврат.

# Часть 6. Модуль за модулем

## 6.1. `main.py` — точка входа

Функция `main()` (async):

1. **Логирование.** `logging.basicConfig(level=..., format=...)`. Уровень из
   `config.LOG_LEVEL`. Если `DEBUG` — «приглушаются» шумные логгеры сторонних
   библиотек (`openai`, `httpcore`, `httpx`, `urllib3`, `asyncio`) до `WARNING`,
   чтобы их внутренний трафик не забивал консоль.
2. **Проверки:** без `BOT_TOKEN` — выход с ошибкой. Пустой `ALLOWED_USER_IDS` —
   предупреждение «доступ запрещён всем».
3. **Bot:** `Bot(token=..., default=DefaultBotProperties(parse_mode=ParseMode.HTML))`.
   HTML — глобальный режим разметки для всех сообщений.
4. **Dispatcher:** `dp = Dispatcher()`.
5. **Preflight (проверка CalDAV до старта):** `await asyncio.to_thread(get_client)` —
   создаёт клиент CalDAV (т.е. реально логинится в Яндекс) и логирует результат.
   Ошибка не останавливает бота — просто пишется в лог.
6. **Регистрация обработчиков:** `dp.include_router(router)` (из `handlers.py`).
7. **Запуск:** `await bot.delete_webhook(drop_pending_updates=True)` (сбросить
   возможный webhook, чтобы polling работал) и `dp.start_polling(bot)`.
8. **Завершение:** в `finally` закрывается `bot.session.close()`.

Запускается через `asyncio.run(main())`.

## 6.2. `config.py` — конфигурация

Разобран в Части 3. Единственная вспомогательная функция — `_int_list(value)`:
«1,2, 3» → `[1, 2, 3]`.

## 6.3. `handlers.py` — Telegram I/O

Полный разбор уже был в Части 5. Дополнительно:

- **`_safe_edit(message, text, reply_markup=None)`** — пробует `edit_text`, а
  если не получится (сообщение уже удалено/нельзя править), отправляет новое
  `answer`. Устойчивость к тому, что пользователь мог удалить сообщение.
- **`_check_allowed`** — защита доступа (см. путь А).
- **`INTRO`** — приветственный текст с примерами запросов.
- **`_PENDING_PLANS: dict[int, str]`** — модульная переменная: `chat_id →

  новое сообщение пользователя отменяло висящий план (`_cancel_pending_plan`).
- **`_handle_result`** — единая точка показа результата агента (текст/вопросы/

иметь `from_user` (тогда берётся `cb.from_user.id`).

## 6.4. `agent.py` — мозг системы (самый важный модуль)

### 6.4.1. Объявления инструментов (`build_tools`, строка 40)

`build_tools()` возвращает список из четырёх схем в формате OpenAI tools
(каждая — `{"type": "function", "function": {"name": ..., "description": ...,
"parameters": {...}}}`). Схемы — это **JSON Schema**: модель видит имена,
описания и параметры, но не видит Python-код.

Разберём каждый инструмент.

**`get_period`** — чтение календаря.
- Параметры: `date_from` (YYYY-MM-DD, включительно), `date_to` (YYYY-MM-DD,
  включительно). **Оба обязательны** (`required` в схеме): модель сама выбирает
  период под запрос.
- Описание подсказывает модели: возвращает пронумерованный список с токенами
  `[eN]`, которые нужны для `reg_list` (серии свёрнуты одной строкой, одиночные —
  по дням).
- **Read-only, исполняется сразу.**

**`reg_list`** — регистрация изменений.
- Параметр `actions` — массив объектов. Каждый элемент имеет `op` в
  `{add, delete, exclude}` и поля конкретного действия.
- Для `add`: `summary`, `start` (YYYY-MM-DDTHH:MM:SS), `duration` (минуты, по
  умолчанию 60), `location`, `description`, `link`, `all_day` (весь день,
  длительность в днях: 1440 = 1 день), `alarms` (минуты до начала, по умолчанию
  [60,15,5]), `categories`, `status`, `transp`, `priority`, `rrule`.
- Для `delete`: только `ref` (токен `[eN]` события/серии **целиком**). Никаких
  `scope`/`date` — операция всегда работает со всем объектом (одиночное событие
  или вся серия).
- Для `exclude`: `ref` (токен **повторяющейся серии**) + `date` (YYYY-MM-DD) —
  внести одно вхождение в список исключений серии (EXDATE).
- **Не пишет в календарь.** Только валидирует и складывает `PlanAction` в план
  сессии. Операции повторяют примитивы CalDAV (`create_event` / `delete_event` /
  `exclude_occurrence`); изменения «1 вхождение» и «правки» выполняются
  комбинацией: исключить/удалить старое + создать новое.

**`ask_user`** — вопрос пользователю.
- Параметры: `question` (текст), `options` (1–4 варианта ответа кнопками
  reply-клавиатуры). Пользователь может выбрать вариант или написать свой ответ.
- **Пауза:** диалог приостанавливается до ответа пользователя; ответ вернётся
  модели как результат инструмента. Задаётся **по одному вопросу за раз**.

**`done`** — завершение хода.
- Параметры: `message` (краткий финальный ответ), `items` (необязательный
  список коротких пунктов — например, найденные события).
- **Терминальный:** фиксирует накопленный план для подтверждения.

После определения `TOOLS = build_tools()` (строка 191).

### 6.4.2. Системный промпт (`SYSTEM_TEMPLATE`, строка 194)

Это текстовая инструкция, которую модель получает каждый раз. Собирается
функцией `build_system_prompt()` с подстановкой текущих даты (`YYYY-MM-DD` и
`ДД.ММ.ГГГГ`), времени и `tz`.

Ключевые правила (нумерованные пункты — нумерация из кода):

1. Ход = обработка одного сообщения/ответа пользователя. Внутри хода — вызовы
   инструментов (get_period, reg_list, ask_user). Каждый ход обязан закончиться
   `done` (финальный ответ) или `ask_user` (пауза, продолжится после ответа).
   Текст без инструментов недопустим. За один вызов можно вернуть несколько
   инструментов (например, get_period + ask_user) — они выполнятся по порядку,
   но вопросы задаются только после сбора данных и по одному за раз.
2. Чтобы найти/посмотреть события — `get_period`; `date_from` и `date_to`
   ОБЯЗАТЕЛЬНЫ. НЕ выдумывать события, даты и факты о календаре.
3. «Ближайшее/следующее/предстоящее» → `get_period` на разумный период вперёд
   (например, от сегодня до +30 дней) и выбрать событие с ближайшей датой. Дату
   самому не угадывать.
4. Если `get_period` вернул «Ничего не найдено» → в `done` ответить «Удалять
   нечего», «Событий нет» и т.п., без выдумок.
5. Выбор события: если запрос однозначно определяет одно событие — брать его
   без вопроса; если несколько одинаково подходят — `ask_user` с вариантами
   (пример: «юайти алгоритмы» — однозначно, просто «юайти» — спросить).
6. Одноразовое событие и повторяющаяся серия с тем же названием — РАЗНЫЕ
   события. `delete` всегда работает с ЦЕЛЫМ объектом (одиночное или вся серия);
   одно вхождение серии удаляется только через `exclude`. Изменение = «удалить
   старое + создать новое».
7. НЕ планировать несколько удалений/изменений за один ход, если пользователь
   явно не просил. Все изменения одного хода — ОДНИМ вызовом `reg_list` со
   списком `actions`. План переживает паузу на `ask_user`; уже
   зарегистрированные действия повторно НЕ регистрировать.
8. Повторяющиеся события: серия — один токен `[eN]`. Для `exclude` нужна дата
   вхождения (из запроса или вычисленная по правилу, с учётом «кроме …»). Если
   пользователь не сказал явно «одно/это вхождение» или «всю серию/все» —
   обязательно спросить через `ask_user` («Удалить одно вхождение или всю
   серию?»). Для «это вхождение» уточнить дату (вариантами дат вхождений).
9. Все изменения — только через `reg_list`. Нельзя писать «сделано/удалено»
   до подтверждения.
10. Создание (`op="add"`): `summary` и `start` обязательны, `duration` в
    минутах (по умолчанию 60). Повтор: «каждый понедельник» →
    `FREQ=WEEKLY;BYDAY=MO` и т.д. Для недельного повтора день недели `start`
    обязан совпадать с `BYDAY`. `all_day: true` + duration в днях.
    Дополнительно: `location`, `description`, `link`, `categories`, `status`,
    `transp`, `priority`.
10а. Напоминания: по умолчанию `alarms: [60, 15, 5]` (за час, 15 и 5 минут),
    если пользователь не просил иное (или `alarms: []` — убрать).
11. Удаление (`op="delete"`): `ref` — токен события/серии целиком. Одно
    вхождение серии — `op="exclude"` с `ref` серии и `date` вхождения.
12. `ask_user`: уточнять ВСЕГДА при неопределённости (какое событие, какая
    дата, одно вхождение или вся серия, какой период); как можно чаще
    предлагать варианты (`options`), пользователь может и написать свой ответ.
    Не переспрашивать явное указание («Вы уверены?» не спрашивать — сразу
    регистрировать план и завершать `done`). По одному вопросу за раз.
13. Отвечать кратко по-русски, без markdown и эмодзи, не упоминать токены
    `ref`. В `done` класть суть в `message`, а перечисление — в `items`.

### 6.4.3. Хранилище: сессии и блокировки

`CalendarAgent` хранит:

- `_lock: threading.RLock` — глобальная блокировка для доступа к словарям
  `_chat_locks` и `_sessions`.
- `_chat_locks: dict[int, threading.RLock]` — по блокировке на каждый `chat_id`.
  Обеспечивает серийную обработку сообщений одного пользователя.
- `_sessions: dict[int, dict]` — сессии (формат в разделе 4.6).
- `_client` — кеш OpenAI-клиента (создаётся лениво).

Методы сессий:

- `_chat_lock(chat_id)` — достать (или создать) блокировку чата.
- `_prune()` — удаляет сессии, у которых `ts` старше
  `AGENT_SESSION_TTL_MIN * 60` секунд. Вызывается в начале `run`/`resume`.
- `_session(chat_id)` — вернуть сессию; если её нет (или протухла) — создать
  новую и обновить `ts`.
- `_append(chat_id, msg)` — добавить сообщение в историю и **обрезать** её
  (`_trim_history`).
- `_append_tool_response(chat_id, tool_call_id, content)` — добавить
  `{"role": "tool", "tool_call_id": ..., "content": ...}`.
- `append_assistant_text(chat_id, text)` — публичный метод: добавить текст
  ассистента (используется из `handlers`, когда план выполнен — модель должна
  узнать о результате).
- `has_pending_asks(chat_id)` — есть ли неотвеченные вопросы.

### 6.4.4. Обрезка истории (`_trim_history`, строка 298)

Важная тонкость: нельзя просто взять `msgs[-limit:]`. Если последние
сообщения — это `tool`-ответы без родительского сообщения с `tool_calls`,
провайдер вернёт ошибку 400 («tool must be a response to tool_calls»).
Поэтому алгоритм: вычисляем «перебор» (`overflow`), и если в позиции среза
стоит `tool` — отступаем дальше, пока не дойдём до не-tool сообщения. Так
пара «assistant с tool_calls → tool-ответы» не разрывается.

### 6.4.5. Вызов LLM (`_ask`, строка 452)

- Если нет `OPENAI_API_KEY` — `AgentError("не настроен OPENAI_API_KEY")`.
- Ленивое создание `OpenAI(api_key=..., base_url=..., timeout=...)`.
- На `DEBUG` в лог выводится весь `messages` (JSON, с отступами) — удобно для
  отладки, но большой лог.
- Тело запроса: `model`, `messages`, `tools=TOOLS`, `tool_choice="auto"`,
  `temperature=0`. Если `OPENAI_THINKING == "disabled"` — добавляется
  `extra_body={"reasoning": {"enabled": False}, "thinking": {"type": "disabled"}}`
  (для DeepSeek-моделей).
- Ответ логируется (content, reasoning, список вызванных функций).
- Любое исключение → `AgentError(f"ошибка LLM: {exc}")`.

### 6.4.6. Чат-цикл (`_loop`, строка 552) — подробно

Псевдокод:

```
for step in 1..AGENT_MAX_STEPS:
    log(шаг, размер истории)
    messages = [system] + history
    choice = _ask(messages).choices[0].message

    if not choice.tool_calls:
        # модель решила ответить текстом — это запрещено
        history += {"role":"assistant","content": текст}
        session["plan"] = []
        return error("Не удалось завершить ход — агент не вызвал done…")

    history += _to_assistant_msg(choice)   # сообщение с tool_calls
    ask_tc = None                          # первый ask_user в пачке
    done_msg = None; done_items = []
    for tc in choice.tool_calls:            # по порядку!
        if tc.function.name == "ask_user":
            if ask_tc is None:
                ask_tc = tc                # запоминаем ПЕРВЫЙ
            else:
                log(игнорирую лишний ask_user)
            continue
        if tc.function.name == "done":
            разобрать message/items
            history += tool("Принято.")
            continue
        result = _call_tool(chat_id, name, arguments)  # get_period / reg_list
        history += tool(result)

    if ask_tc is not None:
        _register_ask(chat_id, ask_tc.id, args)  # вопрос в pending_asks
        questions = [не отправленные (not posted) вопросы]
        пометить их posted
        return ask(questions)                    # ОДИН вопрос за паузу

    if done_msg is not None:
        plan = session["plan"]; session["plan"] = []
        history += {"role":"assistant","content": done_msg}
        return done(text=done_msg, items=done_items, plan=plan)

# цикл кончился без done
session["plan"] = []
return error("Не удалось обработать запрос за отведённое число шагов.")
```

Ключевые решения цикла:

- `tool_choice="auto"` — модель сама решает, звать ли инструмент.
- `temperature=0` — детерминизм.
- Модель может вернуть **пул инструментов** (например, `get_period + ask_user`):
  все выполняются по порядку, результаты `get_period`/`reg_list` попадают в
  историю, пауза наступает на первом `ask_user`. После ответа модель увидит и
  данные календаря, и ответ пользователя.
- Пауза на `ask_user` **приоритетнее** `done` из той же пачки: если в пачке
  был и вопрос, и done — будет `kind="ask"`, а done «потеряется» (но план уже
  накоплен и переживёт паузу — так задумано).
- Лимит шагов защищает от зацикливания (например, модель раз за разом шлёт
  неверный `ref`).

### 6.4.7. `run` / `resume` / `answer_ask`

Разобраны в путях A/B/C. Напомним ключевое:

- `run(chat_id, user_text)`: если есть неотвеченные вопросы — текст становится
  ответом на первый из них (путь C); иначе — добавляется как `user`-сообщение
  и запускается `_loop`.
- `resume(chat_id)`: после того как единственный вопрос паузы отвечен — очищает
  `pending_asks` и продолжает `_loop` (модель может задать следующий вопрос или
  закончить `done`).
- `answer_ask(chat_id, ask_id, content)`: подставляет ответ модели как
  результат инструмента; возвращает `True`, если отвечены все вопросы раунда
  (при «одном вопросе за паузу» — после первого ответа).

### 6.4.8. Инструмент `get_period` (`_tool_get_period`, строка 669)

1. Если нет `date_from` или `date_to` — ошибка «get_period требует date_from и
   date_to (YYYY-MM-DD).» (схема и так требует, это защита).
2. `_resolve_period(args)` вычисляет окно (см. ниже).
3. `caldav_service.list_events(start, end)` — читает календарь и раскрывает
   серии во вхождения (клиентски, через `recurring_ical_events`).
4. Если пусто — возвращает «Ничего не найдено в выбранном периоде.».
5. `format_catalog_compact(events, start, end, oneoff_limit=AGENT_CATALOG_LIMIT)`
   — формирует компактный каталог и словарь refs.
6. `session["refs"] = refs` — токены запоминаются в сессии, чтобы следующий
   ход диалога мог ссылаться на те же `[eN]`.
7. Возвращает текст каталога (он попадёт модели как результат инструмента).

**`_resolve_period(args)` (строка 383):**
- `date_from` → начало дня `date_from`; `date_to` → конец дня `date_to` (до
  полуночи следующего дня). Оба параметра приходят от модели (обязательны);
  ветки «только date_to» и «по умолчанию сегодня + `LIST_DEFAULT_DAYS`»
  оставлены как защита на случай кривых вызовов.

### 6.4.9. Инструмент `reg_list` (`_tool_reg_list`, строка 863) и построение действий

`_tool_reg_list`:
- требует непустой список `actions`;
- для каждого действия вызывает конструктор по `op`:
  - `_build_add` → `PlanAction(kind="create", payload=...)`;
  - `_build_delete` → `PlanAction(kind="delete", event=...)`;
  - `_build_exclude` → `PlanAction(kind="exclude", event=<вхождение>)`;
- ошибка валидации одного действия **не роняет остальные**: ему в строку
  пишется `N. ❌ ошибка`, остальные обрабатываются;
- **дедупликация**: `_action_key(action)` — ключ тождественности. Если такой
  ключ уже есть в плане — пишется `N. ⏭ уже в плане: …` и действие не
  добавляется повторно;
- в ответе — список строк «План зарегистрирован:\n1. ✅ …».

**`_action_key` (строка 896):** для create — `(summary, start ISO, duration,
rrule, alarms)`; для delete — `(ev.url)`; для exclude — `(ev.url, дата
вхождения)`.

**`_build_add` (строка 685):**
- обязательны `summary` и `start` (иначе ошибка с подсказкой формата);
- `_parse_dt(start)` — парсинг `YYYY-MM-DDTHH:MM:SS`, с подстановкой TZ, если
  пояса нет;
- `duration = max(1, int(duration or 60))` → `timedelta(minutes=duration)`;
- `rrule` нормализуется `_normalize_rrule` (снимает префикс `RRULE:`, убирает
  пробелы, проверяет через `vRecur.from_ical`; невалидное — ошибка);
- необязательные поля: `location`, `description` (пустые строки → `None`),
  `all_day` (bool), `alarms` (`_norm_alarms`: список целых минут, >0,
  отсортированный без дублей), `categories` (`_norm_categories`),
  `status`/`transp` (проверка по белому списку), `priority` (`_norm_priority`:
  1–9), `link`.

**`_build_delete` (строка 729):**
- `ref` очищается от скобок `[e1]` → `e1`;
- если токена нет в `session["refs"]` — ошибка «неизвестный ref … Вызови
  get_period заново…»;
- если `refs[ref]` — список (серия), берётся первое вхождение `obj[0]` (это
  «представитель» серии — удалять будем весь ресурс по url); иначе — само
  событие;
- `PlanAction(kind="delete", event=ev)` — **всегда** удаление целого объекта
  (одиночное событие или вся серия). Никаких scope/date.

**`_build_exclude` (строка 743):**
- те же проверки `ref`;
- если `refs[ref]` — НЕ список (одиночное событие) → ошибка «exclude работает
  только для повторяющейся серии. Для одиночного события используй delete.»;
- `_resolve_instance(instances, date)` — найти вхождение серии по дате
  (YYYY-MM-DD). Без `date` — ошибка со списком возможных дат вхождений периода;
  даты нет — ошибка со списком дат;
- `PlanAction(kind="exclude", event=<вхождение>)` — при исполнении в мастер
  добавится `EXDATE`.

### 6.4.10. `ask_user` (`_register_ask`, строка 510)

- разбирает `arguments` (JSON);
- `question` по умолчанию «Пожалуйста, уточните.»;
- `options` — список строк (пустые отбрасываются); если пусто — warning в лог;
- `register_ask_op(AskQ(user_id=chat_id, tool_call_id=..., ...))` — вопрос в
  реестре `asks.py` (для показа reply-клавиатуры);
- в сессию добавляется запись `{ask_id, tool_call_id, question, options,
  posted: False, answered: False}`.

Цикл ставится на паузу ровно на **первом** `ask_user` пачки: в `_loop` берётся
`ask_pending` (первый встреченный), лишние `ask_user` игнорируются. Запись
`posted` нужна, чтобы вопрос не перепостился повторно после возобновления цикла.

## 6.7. `caldav_service.py` — работа с календарём

### 6.7.1. Ошибки и вспомогательные функции

- `CalDAVError(Exception)` — все ошибки CalDAV оборачиваются в неё.
- `_ensure_aware(dt)` — если у datetime нет пояса, считаем его UTC.
- `_parse_dt(value)` — ISO → datetime в TZ пользователя.
- `_norm(dt)` — перевод в TZ пользователя.
- `_get_vevent(cal)` — первый `VEVENT` в `icalendar.Calendar`.
- `_as_dt(value)` — date → datetime (полночь).
- `_is_all_day(value)` — `date`, но не `datetime` (значит «весь день»).
- `_replace_prop(vevent, key, value)` — замена свойства (сначала удалить, потом
  добавить; напрямую перезаписывать нельзя — ломается vCal).

### 6.7.2. Напоминания (VALARM)

- `_get_alarms(vevent)` — собирает относительные `TRIGGER` с отрицательным
  `timedelta` (т.е. до начала события), превращает в минуты: `-PT60M` → 60.
  Сортирует и дедуплицирует.
- `_set_alarms(vevent, minutes)` — удаляет все существующие VALARM и создаёт
  новые: `ACTION:DISPLAY`, `TRIGGER:-PT{m}M`. Пустой список — напоминаний нет.

### 6.7.3. Правка правила повтора (`_patch_rrule`, строка 155)

Умеет частично менять RRULE мастера:

- читает существующий `RRULE` в `parts` (dict: ключ → список значений);
- если передан полный `rrule` — `parts` пересобирается из него целиком;
- `freq` → `parts["FREQ"]` (с проверкой);
- `interval` → `parts["INTERVAL"]`;
- `byday` → `parts["BYDAY"]`;
- `until` — «включить/выключить»: пустая строка убирает `UNTIL`; дата →
  `_until_dt` (если только дата — конец дня в TZ пользователя, переводится в
  UTC); при установке `UNTIL` удаляется `COUNT`;
- `count` → `parts["COUNT"]` (удаляет `UNTIL`);
- если `FREQ` не появился и правила не было — ошибка, если заданы только
  `byday`/`interval` — подставляется `FREQ=WEEKLY`;
- результат через `vRecur` записывается обратно в VEVENT.

### 6.7.4. RDATE / EXDATE

- `_add_rdate(vevent, value)` — добавляет внеплановое вхождение: парсит
  ISO (в TZ → UTC), собирает существующие значения `RDATE`, добавляет новое,
  дедуплицирует, сохраняет через `vDDDLists`.
- `_restore_exdate(vevent, value)` — убирает дату из `EXDATE` (вернуть
  исключённое вхождение). Сравнивает даты с учётом `all_day`. Если после
  удаления `EXDATE` пуст — свойство удаляется (`_drop_prop`).

### 6.7.5. Клиент (`CalDAVClient`, строка 287)

Конструктор:
- создаёт `caldav.DAVClient(url, username, password)`;
- находит principal: `CALDAV_PRINCIPAL_PATH` (если задан) или
  `client.principal()`;
- находит календарь: `CALENDAR_PATH` (прямой URL) → иначе список календарей
  principal → `CALENDAR_ID` (по имени) → иначе первый календарь, имя которого
  не содержит «trash»/«корзин» (пропуск «Корзины» Яндекса).

Синглтон: модульные функции `get_client()` создают клиент один раз под
`_client_lock` (double-checked locking).

### 6.7.6. Чтение: `list_events(start, end)` и `_expand` (строки 337, 353)

1. `self.calendar.events()` — все события календаря (ресурсы на сервере).
2. Для каждого мастера — `_expand(master, start, end)`:
   - `master.icalendar_instance` → `icalendar.Calendar` мастера;
   - `master_vevent = _get_vevent(cal)`;
   - `is_recurring = (RRULE есть)`, `rrule = RRULE.to_ical().decode()`;
   - `exdates = self._exdates_of(master_vevent)` — локальные даты EXDATE
     (для рендера «кроме …»);
   - `occurrences = recurring_ical_events.of(cal).between(start, end)` —
     **раскрытие**: правило повтора превращается в конкретные вхождения в
     диапазоне (EXDATE уже учтены библиотекой);
   - каждое вхождение → `EventData` через `_to_event_data`.
3. Все результаты сортируются по `(start, summary)`.

`_to_event_data(vevent, master, is_recurring, rrule, exdates)`:
- `raw_start = vevent.decoded("DTSTART")`;
- `raw_end`: из `DTEND`, либо из `DURATION`, либо 1 час по умолчанию;
- `all_day` — если DTSTART — чистая дата;
- для all-day: start/end = полуночные datetime в TZ; иначе — `_norm` (в TZ);
- `rdates` — из `RDATE`;
- `categories` — из `CATEGORIES`;
- `instance_start = start if is_recurring else None` — важно для
  `exclude_occurrence`;
- копируется всё остальное (alarms, status, transp, priority, link…).

### 6.7.7. Создание: `create_event(...)` (строка 441)

1. Собирается `icalendar.Calendar` с `prodid` и `version`.
2. `icalendar.Event`:
   - `uid = uuid4()`;
   - `dtstamp = datetime.now(UTC)`;
   - if `all_day`: `dtstart` = дата (без времени), `dtend` = дата +
     `round(duration / 86400)` дней (1440 минут = 1 день);
   - иначе: `dtstart`/`dtend` в UTC (`start_utc + duration`);
   - `summary`, при наличии `rrule` (через `vRecur.from_ical`), `location`,
     `description`;
   - через `_apply_props` — `alarms`, `categories`, `status`, `transp`,
     `priority`, `url`.
3. `self.calendar.save_event(cal.to_ical().decode())` — PUT нового ресурса на
   сервер.
4. Возвращает `EventData` созданного события (если удалось перечитать) или
   «вручную собранный» EventData (fallback).

### 6.7.8. Удаление: `delete_event(ev)` (строка 536)

- `self.calendar.event_by_url(ev.url)` — найти ресурс по URL мастера;
- `target.delete()` — удалить целиком (одиночное событие или вся серия).

### 6.7.9. Исключение вхождения: `exclude_occurrence(ev)` (строка 547)

- требует `ev.instance_start` (иначе ошибка);
- загружает мастер по `ev.url`;
- `raw_start = vevent.decoded("DTSTART")`: если all-day — исключаемая дата
  просто `ev.instance_start.date()`; иначе — `ev.instance_start` в UTC;
- добавляет эту дату в существующий `EXDATE` (дедупликация);
- `vevent["EXDATE"] = vDDDLists(values)`;
- `target.data = cal.to_ical()`; `target.save()` — PUT обновлённого ресурса.

Это и есть «удалить только одно вхождение из серии»: серия остаётся, но дата
попадает в исключения.

### 6.7.10. Изменение мастера: `update_event(ev, changes)` (строка 580)

> **Примечание:** метод оставлен в сервисе для совместимости, но агент его
> больше **не вызывает** — операция `update` из `reg_list` убрана. Все правки
> агент делает комбинацией `add`/`delete`/`exclude`.

1. Загружает мастер, читает `raw_start`, определяет `all_day`,
   `old_start`, `old_duration`.
2. `new_start`: из `changes["start"]` (ISO) либо `old_start +
   shift_minutes`. `new_duration`: из `changes["duration"]`, иначе прежняя.
3. Переключение `all_day` ↔ по времени (с пересчётом длительности).
4. Правки полей: `SUMMARY`, `LOCATION`, `DESCRIPTION` (пустая строка —
   удалить свойство), `alarms`, `categories`, `status`, `transp`, `priority`,
   `url`.
5. Правка правила повтора, если меняется `rrule/until/count/freq/interval/byday`.
6. `add_occurrence` → `_add_rdate`; `restore_occurrence` → `_restore_exdate`.
7. `_set_start(vevent, new_start, new_duration, all_day)`:
   - удаляется `DURATION` (используем явный DTEND);
   - all-day: даты без времени; иначе: в UTC.
8. `target.data = cal.to_ical(); target.save()`.

### 6.7.11. Изменение одного вхождения серии: `update_instance(ev, changes)` (строка 677)

> **Примечание:** метод оставлен в сервисе для совместимости, но агент его
> больше **не вызывает**. Изменение одного вхождения агент выполняет как
> `exclude` (исключить дату) + `add` (создать новое событие).

Классическая техника «отвязанного вхождения» (detached instance):

1. Загружает мастер.
2. Определяет `master_all_day`, часовой пояс мастера.
3. `inst_start = ev.instance_start` (в поясе мастера).
4. `new_start`: из `changes["start"]` или `inst_start + shift_minutes`.
5. `new_duration`: из `changes["duration"]`, иначе `ev.duration`.
6. Создаёт **отдельный** `VEVENT` (внутри того же ресурса, рядом с мастером):
   - тот же `UID`, что у мастера (это ключ: «это перекрытие серии»);
   - `dtstamp`, `sequence = master.SEQUENCE + 1`;
   - `recurrence-id` = дата/дата-время вхождения — указывает, какое вхождение
     серии это перекрывает;
   - новые `dtstart`/`dtend`;
   - `summary` (новое или мастеровое), `location`, `description`, `categories`,
     `status`, `transp`, `priority`, `url`, `alarms` — из `changes` или из
     мастеровых.
7. `cal.add_component(det)`; сохранить ресурс.

Итог в календаре: мастер-серия + отдельный VEVENT с `RECURRENCE-ID`, который
«затмевает» стандартное вхождение на эту дату. Именно поэтому при переносе
одного вхождения в календаре видно две записи: серия без этой даты (если она
была исключена) и новое событие. В текущей реализации `update_instance` не
добавляет `EXDATE` — перекрытие и так скрывает мастеровое вхождение на эту
дату (зависит от клиента календаря).

### 6.7.12. Модульный фасад

Внизу файла: `get_client()`, `list_events(...)`, `create_event(...)`,
`delete_event(...)`, `exclude_occurrence(...)`, `update_event(...)`,
`update_instance(...)` — тонкие обёртки над синглтоном.

Фасад `create_event` (строка 804) повторяет сигнатуру метода класса
`CalDAVClient.create_event`: принимает `summary, start, duration, location,
description, rrule` и необязательные `all_day, alarms, categories, status,
transp, priority, link` — ровно те ключи, которые кладёт в `payload`
`agent._build_add`. Поэтому `handlers._run_create_action`, вызывающий
`create_event(**payload)`, корректно передаёт все поля плана вплоть до
создания события на сервере.

## 6.8. `formatting.py` — рендер текстов

Два разных «лица»: каталог для модели (без HTML, компактный) и тексты для
человека (с HTML, эмодзи, красивым списком).

### 6.8.1. Даты по-русски

- `WEEKDAYS = ["Пн","Вт",...]`, `MONTHS_GEN = ["января",...]`.
- `fmt_date(d)` → «Пн, 10 августа».
- `fmt_dtime(dt)` → «сегодня» / «завтра» / «Пн, 10 августа».

### 6.8.2. `describe_rrule(rrule)` (строка 67)

Превращает строку RRULE в русскую фразу: `FREQ=WEEKLY;BYDAY=MO` → «каждый Пн»;
`FREQ=WEEKLY;BYDAY=MO,TU` → «каждый Пн и Вт»; `FREQ=MONTHLY;BYDAY=1SU` →
«каждый первый Вс месяца»; `FREQ=DAILY` → «каждый день»; `INTERVAL=2` → «раз в
2 недели»; `UNTIL=...` → «до Сб, 10 августа»; `COUNT=5` → «5 раз».

### 6.8.3. `describe_event(ev)` (строка 145)

Плоское описание события для каталога LLM:
`Название · Пн, 10 августа, 16:00–17:00 · каждый Пн · место · описание ·
напоминания за 60, 15, 5 мин · категории: ...`

### 6.8.4. `format_catalog_compact(events, start, end, oneoff_limit)` (строка 167)

Возвращает кортеж `(text, refs)`.

- `events` — список `EventData` (все вхождения периода).
- События делятся: `is_recurring` → в `series` (группируются по `ev.url`),
  иначе → в `oneoffs`.
- **Серии** выводятся ОДНОЙ строкой (по представителю `insts[0]`):
  `[eN] Название · 16:00–17:00 · каждый Пн · кроме Пн, 10 августа ·
  напоминания … · категории …`. «Кроме …» показывает `exdates` мастера,
  отфильтрованные по периоду.
- **Одиночные** — по дням: `Пн, 10 августа:` затем `  [eN] описание`.
- Токены `[eN]` нумеруются сквозняком (и в сериях, и в одиночных) — каждый
  уникален в пределах периода.
- `refs`: серия → список вхождений периода (`list[EventData]`), одиночное →
  `EventData`.
- `oneoff_limit` — максимум показанных одиночных; если их больше — строка
  «(показаны первые N одиночных из M)».

Пример возврата инструмента `get_period`:

```
Серии:
  [e1] Занятие математика · 16:00–17:00 · каждый Пн
  [e2] Вычесывание бобров · 16:00–17:00 · каждый Пн · кроме Пн, 10 августа

Одиночные события:
Пн, 10 августа:
  [e3] прогулка с Катей · Пн, 10 августа, 13:00–14:00
```

### 6.8.5. Человеческие тексты

- `format_ask(question)` → `❓ {question}` (HTML-экранирование).
- `format_done(message, items)` → сообщение + список «Детали»: строки,
  начинающиеся с «Серии» — жирные с 🔁, «Одиночные» — с 📅, остальные — буллеты.
- `format_plan(actions)` → `<b>📋 План действий</b>` + нумерованный список
  строк `_plan_action_line(a)` + «Выполнить?».
- `_plan_action_line(a)` — читаемое описание одного действия:
  - create: «✨ Создать «…» — Пн, 10 августа, 20:00–21:00 · 🔁 … · 📍 … · 🔔 …»;
  - delete: «🗑 Удалить все повторения «…»» / «🗑 Удалить «…» (завтра, 17:00)»;
  - update: «📝 Изменить «…» (это вхождение): название → «…», начало → 19:00,
    …» (все поддерживаемые поля).
- `_new_start(ev, changes)` — новая дата начала: из `changes["start"]` или
  `ev.start + shift_minutes`.

# Часть 7. Потоки, блокировки и асинхронность (как это не ломается)

События происходят в разных местах и в разных потоках. Разберём, как это
скоординировано.

## 7.1. Event loop aiogram

Все Telegram-обработчики (`on_message`, `on_callback`)
выполняются в event loop (один поток). Внутри них **нельзя** долго блокировать
поток — иначе бот перестанет отвечать. Поэтому долгие синхронные операции
запускаются так:

```python
result = await asyncio.to_thread(run_agent, message.from_user.id, text)
```

`asyncio.to_thread` берёт обычную функцию и выполняет её в потоке из пула
(ThreadPoolExecutor), возвращая awaitable. Event loop при этом свободен и может
обрабатывать другие Update'ы.

## 7.2. Блокировки внутри агента

- **`CalendarAgent._lock`** — RLock для защиты словарей `_sessions`,
  `_chat_locks`.
- **`_chat_lock(chat_id)`** — пер-чатовый RLock. Весь ход обработки одного
  сообщения (`run`/`resume`/`answer_ask`) выполняется внутри
  `with self._chat_lock(chat_id)`. Это гарантирует, что для одного
  пользователя сообщения обрабатываются последовательно и не перемешиваются.
  Разные пользователи обрабатываются параллельно (в разных потоках).

## 7.3. Блокировки CalDAV

`CalDAVClient._lock` — RLock вокруг всех сетевых операций с сервером
(`list_events`, `create_event`, `delete_event`, `exclude_occurrence`). Плюс
синглтон `get_client()` защищён отдельным `_client_lock` при создании
(double-checked locking). Зачем: один клиент общий для всех, и правки одного
потока не должны конфликтовать с чтением другого.

## 7.4. Итоговая картина

- Один Update обрабатывается: aiogram event loop → `to_thread` → поток из пула
  → агент (с блокировкой чата) → CalDAV (с блокировкой клиента).
- «Гонка» возможна только если один пользователь напишет два сообщения почти
  одновременно — но пер-чатовая блокировка сериализует их.

# Часть 8. Безопасность (по пунктам)

1. **Запись — только по кнопке.** Ни одна ветка `reg_list` не вызывает
   `create_event`/`delete_event`/`exclude_occurrence`. Все эти
   функции вызываются только из `handlers._perform_plan` после
   `plan_confirm`. В промпте это тоже зафиксировано («изменения НЕ выполняешь
   сам»).
2. **Планировщик и исполнитель разделены.** Модель может только читать
   (`get_period`) и «черновиковать» план (`reg_list`). Реальное исполнение —
   обычный код без ИИ.
3. **Двухшаговый деструктив.** План показывается списком, и удаление даже
   «по плану» требует явной кнопки.
4. **Доступ по `ALLOWED_USER_IDS`.** Проверка в каждом текстовом и
   callback-обработчике (`_check_allowed`).
5. **Проверка владельца операции.** В `on_callback` проверяется
   `cb.from_user.id == op.user_id`.
6. **TTL операций.** Планы (`confirmation.py`) и вопросы (`asks.py`) живут 15
   минут и чистятся `cleanup_expired()`.
7. **Лимит шагов** `AGENT_MAX_STEPS` — модель не может крутить цикл бесконечно.
8. **Валидация аргументов инструментов** (даты, RRULE, ref, enum'ы, числа) —
   модель не протолкнёт мусор в план.
9. **Строгий `done`.** Ход без терминального `done`/`ask_user` — ошибка, план
   при этом очищается.
10. **«Не выдумывать».** Промпт требует сначала `get_period`; даже если модель
    «захотела бы» что-то выдумать, read-only слой не даст ей писать.
11. **Одноразовость операций.** `consume` извлекает операцию из реестра — по
    одной кнопке можно выполнить план только один раз.
12. **Отмена старого плана.** Новое сообщение пользователя отменяет висящий
    неподтверждённый план (`_cancel_pending_plan`).
13. **HTML-экранирование.** Весь пользовательский/событийный текст, попадающий
    в HTML-сообщения, проходит через `esc()` из `html` — защита от
    «инъекции» в разметку.

# Часть 9. Сквозные сценарии

## 9.1. «Удали ближайшее вычесывание бобров»

Сегодня пятница 07.08. Есть серия «Вычесывание бобров» по понедельникам 16:00,
и 10.08 есть перенесённое одноразовое в 17:00.

1. Пользователь пишет текст → `on_message` → `run_agent`.
2. Шаг 1 цикла: модель зовёт `get_period(date_from="2026-08-07", date_to="2026-09-06")`
   (даты обязательны, период модель выбирает сама). `_tool_get_period`
   читает календарь, `format_catalog_compact` строит каталог:
   ```
   Серии:
     [e1] Вычесывание бобров · 16:00–17:00 · каждый Пн
   Одиночные события:
   Пн, 10 августа:
     [e2] Вычесывание бобров · Пн, 10 августа, 17:00–18:00
   ```
   `session["refs"]` = `{e1: [вхождения серии], e2: EventData(10.08)}`.
3. Шаг 2: модель видит два события с одинаковым названием (по правилам 4–6 —
   спросить) → вызывает `ask_user(question="Какое удалить?", options=[...])`.
   `kind="ask"`; вопрос уходит в чат с reply-клавиатурой.
4. Пользователь жмёт кнопку (или пишет текст) → текст приходит в `on_message` →
   `run` трактует его как ответ на вопрос → цикл продолжается.
5. Шаг 3: модель зовёт `reg_list(actions=[{op:"delete", ref:"e2"}])` — план
   сессии = [delete 10.08] (`delete` всегда удаляет целый объект).
6. Шаг 4: `done(message="Запланировал удаление…")` → `kind="done"`, план
   забирается, `session["plan"]` очищается.
7. `handlers`: `PlanOp` → `register` → сообщение «…📋 План действий 1. 🗑
   Удалить «Вычесывание бобров» (Пн, 10 августа, 17:00)» + кнопки.
8. Пользователь жмёт «✅ Выполнить всё» → `_perform_plan` → `_run_delete_action`:
   событие 10.08 — одноразовое → `delete_event(ev)` (удаление ресурса) →
   «✅ Удалено: «Вычесывание бобров»». История агента дополняется результатом.

## 9.2. «Перенеси юайти на час позже» (одно вхождение серии)

Пользователь имеет в виду одно вхождение серии «Юайти олпрактика».

1. Модель зовёт `get_period`, находит серию `[eN]`.
2. По правилам — уточняет: `ask_user` («Удалить одно вхождение или всю
   серию?»), затем, если нужно, вопрос о дате. Вопросы задаются **по одному**:
   ответ на первый → цикл → следующий вопрос.
3. После ответов: `reg_list(actions=[{op:"exclude", ref:"eN", date:"<дата>"},
   {op:"add", summary:"Юайти олпрактика", start:"<дата>T+1ч", duration:60}])` —
   исключить старое вхождение + создать новое событие на час позже.
4. `done(...)` → план → кнопка → подтверждение.
5. `_perform_plan`: `exclude_occurrence(ev)` (в мастер добавляется `EXDATE` на
   эту дату) и `create_event(...)` (новое событие).
6. Результат: «✅ Исключено вхождение: «Юайти олпрактика» (…)» и «✅ Создано:
   «Юайти олпрактика» (…)».

## 9.3. «Создай встречу с Аней завтра в 14:00 на час»

1. `get_period` может не понадобиться — модель может сразу `reg_list(actions=[
   {op:"add", summary:"Встреча с Аней", start:"<завтра>T14:00:00",
   duration:60}])`.
2. `_build_add` валидирует и формирует `payload` → план.
3. `done(...)` → план → кнопка.
4. `_run_create_action` → `create_event(summary=..., start=..., duration=...)`
   → «✅ Создано: «Встреча с Аней» (завтра, 14:00)».

## 9.4. «Отмени завтрашнее занятие» в серии

1. `get_period` → серия `[e1]`.
2. `ask_user` про «одно вхождение или всю серию» → пользователь выбирает «это
   вхождение», затем уточняется дата.
3. `reg_list(actions=[{op:"exclude", ref:"e1", date:"<дата>"}])`.
4. `done(...)` → кнопка → `_run_exclude_action` → `exclude_occurrence(ev)` — в
   мастер добавляется `EXDATE` на эту дату.
5. Результат: «✅ Исключено вхождение: «…» (завтра, 16:00)».

# Часть 10. Как отлаживать

1. **`LOG_LEVEL=DEBUG`** в `.env` (и в `config.py`, `main.py`, `agent_demo.py`
   учтён). На DEBUG агент печатает:
   - весь `messages` перед каждым вызовом LLM (JSON);
   - ответ модели: content, reasoning, имена вызванных функций;
   - каждый шаг цикла: `AGENT chat=... шаг=N ...`, вызовы инструментов с
     аргументами и результатами, паузы, ответы на вопросы, возобновления,
     `done` с числом действий плана.
   Шумные логгеры (`openai`, `httpcore`, `httpx`, `urllib3`, `asyncio`)
   приглушаются до WARNING.
2. **`agent_demo.py`** — быстрая проверка логики агента без Telegram.
3. **`check_connection.py`** — проверка кредов CalDAV до запуска бота.

# Часть 11. Известные ограничения

- **Память, не БД.** Сессии, планы и вопросы живут in-memory: рестарт бота
  теряет диалоги и ожидающие подтверждения.
- **Провайдер должен поддерживать function calling.** Часть локальных vLLM не
  поддерживает tools полностью.
- **Одно сообщение = один поток.** Синхронная обработка в потоке; при большом
  календаре история растёт — ограничивается `AGENT_CATALOG_LIMIT` и
  `AGENT_HISTORY_LIMIT`.
- **Даты вхождений для `exclude` вычисляет модель.** Каталог серии компактный
  (одна строка), конкретные даты вхождений модель берёт из запроса пользователя
  или высчитывает по правилу повтора (например, «следующий понедельник») с
  учётом исключений «кроме …». Ошибка модели → `exclude` не найдёт дату и вернёт
  ошибку со списком возможных дат периода.
- **`update_event` / `update_instance` в сервисе не используются агентом.**
  Методы оставлены для совместимости; агент работает только через
  `create_event` / `delete_event` / `exclude_occurrence`. При «изменении» дата
  может «поехать» как два события (исключённое + новое).
