# AI-CalDav-Bot — как устроен проект

Телеграм-бот для управления Яндекс-календарём (CalDAV) через естественный язык.
Вместо классической схемы «распарсил команду → выполнил» здесь используется
**агентная архитектура**: языковая модель работает как агент с инструментами
(function calling) и сама решает, какие действия предложить, но никогда не пишет
в календарь напрямую.

```
┌────────────┐  сообщение   ┌─────────────────────────────┐
│  Telegram   │ ───────────► │ handlers.on_message          │
│  (aiogram)  │ ◄─────────── │  (aiogram Router)            │
└────────────┘  ответ/кнопка └──────────────┬──────────────┘
                                            │ run_agent(chat_id, text)   (в отдельном потоке)
                                            ▼
                                   ┌────────────────────┐
                                   │ agent.CalendarAgent │   ← LLM с tools
                                   │  · чат-цикл          │
                                   │  · сессии + refs     │
                                   └─────────┬──────────┘
                       read-only tools (list_events) │ mutations (propose_*) → план
                                            ▼
                                   ┌────────────────────┐
                                   │  result.text       │
                                   │  result.plan       │   (PlanAction[])
                                   └─────────┬──────────┘
                                если план непуст:
                                            ▼
                                   PlanOp → кнопка «✅ Выполнить всё / ❌ Отмена»
                                            ▼
                                   handlers._perform_plan → caldav_service (скрипт, не ИИ)
```

Ключевой принцип безопасности повторяется в нескольких местах кода и в промпте:
**LLM планирует, скрипт исполняет**. У нейросети нет доступа к записи в календарь —
только к чтению и к «черновику» плана, который подтверждает человек кнопкой.

---

## 1. Компоненты

| Файл | Роль |
|---|---|
| `main.py` | Точка входа: создаёт `Bot`/`Dispatcher` aiogram, проверяет подключение к CalDAV, запускает polling. |
| `handlers.py` | Telegram-I/O: принимает текст, запускает агента, показывает план с кнопкой, исполняет план после подтверждения. |
| `agent.py` | **Агент**: схемы инструментов, системный промпт, чат-цикл, сессии, исполнение read-only инструментов. |
| `confirmation.py` | `PlanAction` / `PlanOp`, реестр «ожидающих операций» (TTL 15 мин), клавиатура подтверждения. |
| `caldav_service.py` | CRUD поверх CalDAV: чтение с раскрытием повторов, создание, удаление, `EXDATE`, изменение. |
| `formatting.py` | Рендер: каталог для модели (`format_catalog`), план для человека (`format_plan`), даты и RRULE по-русски. |
| `config.py` | Все настройки из `.env`. |
| `agent_demo.py` | CLI-песочница: гоняем агента без Telegram. |
| `check_connection.py` | CLI-проверка доступа к Яндексу. |

Зависимости: `aiogram` (бот), `caldav` + `icalendar` (протокол и iCal), `recurring-ical-events`
(раскрытие повторов), `openai` SDK (LLM), `python-dotenv` (конфиг). Подробнее — `requirements.txt`.

## 2. Жизненный цикл сообщения (пошагово)

1. Пользователь пишет фразу в Telegram.
2. `handlers.on_message` (`handlers.py:107`):
   - проверяет доступ (`ALLOWED_USER_IDS`);
   - чистит протухшие операции (`cleanup_expired`);
   - шлёт индикатор «печатает» (`ChatAction.TYPING`);
   - **отменяет предыдущий незакрытый план** для этого чата (`_cancel_pending_plan`);
   - вызывает `run_agent(chat_id, text)` в отдельном потоке (`asyncio.to_thread`), чтобы не блокировать
     event loop aiogram.
3. Агент (`agent.run`) крутит чат-цикл: зовёт LLM, выполняет `list_events`, накапливает `propose_*`
   в план, пока модель не вернёт финальный текст.
4. `run_agent` возвращает `AgentResult{text, plan}`.
5. **Если план непуст**: создаётся `PlanOp`, в сообщение кладётся `format_plan(plan)` + кнопка
   «✅ Выполнить всё / ❌ Отмена». Обычный текст агента идёт выше списка действий.
6. **Если план пуст**: пользователю просто отправляется `result.text` — это может быть список событий,
   ответ «Удалять нечего» или уточняющий вопрос.
7. По кнопке:
   - «✅ Выполнить всё» → `handlers._perform_plan` исполняет каждое действие через `caldav_service`
     и заменяет сообщение списком результатов. Результат также дописывается в историю агента
     (`append_assistant_text`), чтобы следующий ход диалога «знал» о сделанном.
   - «❌ Отмена» → «Отменено», операция удаляется из реестра.

## 3. Агент (`agent.py`) — самое важное

### 3.1 Идея

LLM — «планировщик». Она видит:
- системный промпт с текущей датой/временем/таймзоной;
- историю диалога (роли `user`/`assistant`/`tool`);
- объявления инструментов (`TOOLS`).

Модель может **вызывать инструменты** (возвращать `tool_calls` вместо обычного текста).
Скрипт исполняет инструменты и подкладывает результаты обратно в историю как сообщения роли `tool`,
после чего зовёт модель ещё раз. Так продолжается, пока модель не вернёт обычный текст.

### 3.2 Инструменты (`TOOLS`, `agent.py:31`)

Всего четыре функции:

| Инструмент | Тип | Что делает |
|---|---|---|
| `list_events(date_from?, date_to?, query?)` | **read-only, исполняется сразу** | Ищет события в периоде, возвращает нумерованный каталог `[e1] …`. |
| `propose_create(summary, start, duration?, location?, description?, rrule?)` | staged | Кладёт «создание» в план. |
| `propose_delete(ref, scope=instance\|all)` | staged | Кладёт «удаление» в план. |
| `propose_update(ref, scope, changes)` | staged | Кладёт «изменение» в план. |

Почему `propose_*`, а не `create_*`: инструменты с префиксом `propose` **не пишут в календарь**.
Они лишь валидируют аргументы и добавляют `PlanAction` в `self._plan`. Финальное слово — за кнопкой.

### 3.3 `list_events` — как агент «видит» календарь

При вызове (`_tool_list_events`, `agent.py:359`):
1. `_resolve_period` определяет окно:
   - есть `date_from` → день начала; если есть `date_to` → до конца этого дня (включительно);
   - только `date_to` → этот день;
   - ничего → **сегодня + `LIST_DEFAULT_DAYS`** (по умолчанию 90 дней).
2. `caldav_service.list_events(start, end)` читает календарь и **раскрывает повторяющиеся серии**
   в отдельные вхождения через `recurring_ical_events`.
3. `collapse_events` свёртывает серию обратно в **одного представителя** — первое вхождение в окне
   (для серии это ближайшее будущее вхождение). Модель не тонет в десятках строк одного повтора,
   но видит дату ближайшего вхождения.
4. Если задан `query` — фильтр по подстроке в названии/месте/описании (служебная оптимизация;
   модель может и без него, просто прочитав каталог).
5. `format_catalog` нумерует события токенами `[e1]…[eN]` и возвращает текст + словарь `{ref: EventData}`.
6. Словарь refs кладётся в **сессию** (`session["refs"]`), чтобы последующие сообщения диалога могли
   ссылаться на те же токены.

Пример возврата инструмента:

```
[e1] прогулка с Катей · Сб, 8 августа, 13:00–14:00
[e2] Русский репетитор · Сб, 8 августа, 18:30–20:00
```

Если событий нет — возвращается строка `«Ничего не найдено в выбранном периоде.»`, и промпт
требует ответить «Удалять нечего» / «Событий нет», ничего не выдумывая.

### 3.4 Чат-цикл (`CalendarAgent.run`, `agent.py:305`)

```
run(chat_id, user_text):
  1. _prune()                     # убрать сессии, старше AGENT_SESSION_TTL_MIN
  2. добавить в историю: {"role":"user","content": user_text}
  3. план = []
  4. for step in 1..AGENT_MAX_STEPS (по умолчанию 8):
       messages = [system(сегодня/время/tz)] + история сессии
       ответ = LLM(messages, tools=TOOLS, tool_choice="auto", temperature=0)
       if у ответа нет tool_calls:            # модель закончила
           история += {"role":"assistant","content": текст}
           return AgentResult(text, plan)
       история += assistant-сообщение с tool_calls
       for каждый tool_call:
           результат = исполнение инструмента (например list_events)
           история += {"role":"tool","tool_call_id":…,"content": результат}
  5. лимит шагов исчерпан → AgentResult("Не удалось…", план)
```

Особенности:
- `tool_choice="auto"` — модель сама решает, звать ли инструмент.
- `temperature=0` — детерминированные решения.
- Каждый виток LLM отправляет **всю историю сессии** (+ свежий system-промпт с текущей датой),
  поэтому модель помнит предыдущие сообщения и предыдущие каталоги.
- Лимит шагов защищает от зацикливания (например, когда модель раз за разом шлёт неверный `ref`).
- Ошибка LLM оборачивается в `AgentError` и уходит пользователю как «😕 Ошибка агента: …».

### 3.5 Сессии и refs

- Сессия — это `dict` в памяти: `{chat_id: {"messages": [...], "refs": {...}, "ts": float}}`.
- Хранится в `CalendarAgent._sessions`, закрыта `threading.RLock`.
- TTL — `AGENT_SESSION_TTL_MIN` (по умолчанию 30 мин), чистка при каждом вызове `run`.
- История обрезается до `AGENT_HISTORY_LIMIT` (по умолчанию 30) последних сообщений.
- `refs` живут в сессии специально: модель на следующем сообщении может сослаться на `[e1]` из
  предыдущего каталога, не перечитывая календарь. Это и есть источник естественного диалога
  («Какие события завтра?» → «Перенеси прогулку на час позже»).
- Сессии in-memory: после рестарта бота диалог обнуляется.

### 3.6 Системный промпт (`SYSTEM_TEMPLATE`, `agent.py:121`)

Промпт собирается каждый вызов через `build_system_prompt()` и подставляет
`Сегодня / Сейчас / Часовой пояс`. Правила (в сокращении):
1. Никогда не выдумывать события — сначала `list_events`.
2. «Ближайшее/следующее» → `list_events` без дат (90 дней) и выбор ближайшей даты.
3. Пустой результат → «Удалять нечего», без выдумок.
4. Несколько кандидатов → выбрать очевидное или спросить уточнение обычным текстом.
5. Одноразовое событие и серия с тем же названием — **разные** события; «все повторения» = только серия.
6. Не планировать несколько действий за ход, если пользователь не просил несколько.
7. Повторяющиеся: `instance` = одно вхождение, `all` = вся серия; при неясности — спросить или `instance`.
8. Изменения — только через `propose_*`; до подтверждения писать «сделано/удалено» нельзя.
9. Мульти-действия разрешены (несколько `propose_delete` + `propose_create` за один ответ).
10. Создание: обязательны `summary` и `start`; повторы через RRULE; для недельного повтора день недели
    `start` обязан совпадать с `BYDAY` (иначе берётся ближайший подходящий).
11. Перенос не меняет длительность, если не просили.
12. Отвечать кратко по-русски, без markdown/эмодзи, без упоминания `ref`.

### 3.7 Валидация в `propose_*`

Инструменты проверяют аргументы, прежде чем положить действие в план:
- `propose_create`: наличие `summary`/`start`, парсинг даты, `duration ≥ 1`, валидация RRULE
  (`vRecur.from_ical` после нормализации). Итог — словарь `payload`.
- `propose_delete`: `ref` обязан существовать в `session["refs"]` (иначе ошибка с подсказкой
  «вызови list_events заново»), `scope` приводится к `instance`/`all`.
- `propose_update`: тот же `ref`-чек, `changes` непустые и содержат хотя бы одно из
  `summary/start/shift_minutes/duration/location`, строки подчищаются.

Каждое действие получает номер («Действие 2 запланировано: …») — модель может планировать их пачкой,
и номера помогают ей не путаться.

### 3.8 Debug-логирование

На уровне `DEBUG` (`logger = logging.getLogger(__name__)`) агент печатает:
```
AGENT chat=777003 шаг=1 вызов LLM (история=3 сообщений)
AGENT chat=777003 шаг=1 tool=list_events args={"date_from":"2026-08-08","date_to":"2026-08-08"}
AGENT chat=777003 шаг=1 tool=list_events result='[e1] прогулка с Катей · Сб, 8 августа, 13:00–14:00'
AGENT chat=777003 шаг=2 tool_calls=1
AGENT chat=777003 шаг=2 tool=propose_update args={"ref":"e1","scope":"instance","changes":{"start":"..."}}
AGENT chat=777003 шаг=2 tool=propose_update result='Действие 1 запланировано: …'
AGENT chat=777003 шаг=3 финальный ответ: 'Я запланировал …'
```
Это удобно при отладке: видно каждый шаг цикла, аргументы и результаты инструментов.
`main.py` по умолчанию включает `INFO`; чтобы увидеть шаги, поднимите уровень до `DEBUG`.

## 4. Подтверждение и исполнение плана

### 4.1 `confirmation.py`

- `PlanAction` — одно действие плана: `kind` (`create`/`delete`/`update`), `event` (для delete/update —
  это `EventData` из refs, с `url` и `instance_start`), `payload` (для create), `scope`
  (`instance`/`all`/`single`), `changes` (для update).
- `PlanOp` — `{user_id, actions}`.
- Реестр `PENDING: dict[op_id, BaseOp]` + `_CREATED_AT`. Время жизни операции — `OP_TTL_SECONDS = 900`
  (15 минут), чистка `cleanup_expired()`.
- `register/get/consume` — создать, получить, забрать (и удалить) операцию.
- `kb_plan_confirm(op_id)` — инлайн-кнопки `✅ Выполнить всё` / `❌ Отмена`, callback `op:<id>:plan_confirm`.

### 4.2 Callback (`handlers.on_callback`, `handlers.py:138`)

- Парсится `op:<id>:<action>`.
- Операция обязана существовать и принадлежать тому же пользователю (`cb.from_user.id == op.user_id`).
- `cancel` → сообщение «❌ Отменено».
- `plan_confirm` → `consume` операцию, `_perform_plan` в потоке, сообщение заменяется результатами,
  результат дописывается в историю агента.

### 4.3 Исполнение (`handlers.py:179`)

`_perform_plan` проходит по `op.actions` и вызывает `_perform_action`. Любое `CalDAVError`
не роняет остальные действия — ошибка просто попадает отдельной строкой в результат.

- **create** → `create_event(**payload)` → «✅ Создано: «Название» (…, ЧЧ:ММ) 🔁 каждый Пн».
- **delete**:
  - `scope == "all"` или событие не повторяется → `delete_event(ev)` (удаление ресурса);
  - иначе → `exclude_occurrence(ev)` (добавление `EXDATE` — исключение одного вхождения).
- **update**:
  - повторяющееся и `scope == "instance"` → сначала `exclude_occurrence(ev)`, затем `create_event`
    нового отдельного (неповторяющегося) события с изменёнными полями — классическая техника
    «отменить вхождение в серии + создать копию»;
  - иначе → `update_event(ev, changes)` (правка мастера-события).

`_build_updated_payload` вычисляет новые поля из старых: `start` через `_new_start`
(приоритет `start`, иначе `shift_minutes`), длительность сохраняется, если не задана.

## 5. CalDAV-слой (`caldav_service.py`)

- `CalDAVClient` — ленивый одиночка (модульный фасад `get_client`), `threading.RLock` на все запросы.
  Дискавери: `_find_principal` / `_find_calendar` (прямой `CALENDAR_PATH`, либо выбор по `CALENDAR_ID`,
  либо первый не-«Корзина»).
- `list_events(start, end)` — `calendar.events()` → для каждого мастера `_expand`:
  `recurring_ical_events.of(cal).between(start, end)` раскрывает серии во вхождения
  (с учётом `EXDATE`/`RDATE`). Поле `is_recurring` берётся из наличия `RRULE`.
- `collapse_events` — группирует вхождения по `url` мастера, оставляет представителя с полями
  `series_count`, `series_first`, `series_last`.
- `create_event(summary, start, duration, location, description, rrule)` — собирает `icalendar.VEVENT`
  с `uuid4`-UID, `DTSTART/DTEND` в UTC, `RRULE` через `vRecur`, сохраняет `calendar.save_event`.
- `delete_event(ev)` — `event_by_url(ev.url).delete()` (весь ресурс).
- `exclude_occurrence(ev)` — перезагружает мастер по URL, добавляет `EXDATE`
  (дата для all-day, `datetime` в UTC для обычных), сохраняет.
- `update_event(ev, changes)` — правит `SUMMARY/LOCATION/DTSTART/DTEND` мастера
  (`start` из ISO, либо `shift_minutes`), при смене времени пересчитывает `DTEND` от новой даты.

Тонкость про «перенести 10 августа на час позже»: агент предлагает `propose_update(scope=instance)` →
скрипт исключает 10.08 из серии (`EXDATE`) и создаёт одноразовое событие на 10.08 в новое время.
Именно поэтому в календаре появляются две записи: серия без 10.08 + отдельное событие.

## 6. Форматирование (`formatting.py`)

Два разных рендера — для машины и для человека:

- `format_catalog(events) -> (text, refs)` — плоский текст для LLM: `[eN] <описание>`.
  Описание через `describe_event` (дата, время, RRULE, место, описание) — без HTML и эмодзи.
- `format_plan(actions)` — красивый список для Telegram (HTML): 
  ```
  📋 План действий
  1. 🗑 Удалить «Вычесывание бобров» (Пн, 10 августа, 17:00)
  2. ✨ Создать «Встреча с Аней» — Пн, 10 августа, 20:00–21:00
  ```
- Вспомогательное: `fmt_date`/`fmt_dtime` (русские даты, «сегодня»/«завтра»), `describe_rrule`
  (RRULE → «каждый Пн»), `_new_start` (вычисление новой даты начала из `changes`).

## 8. Безопасность

1. **Запись только по кнопке.** Ни одна `propose_*`-ветка не вызывает `create_event/delete_event/update_event`;
   они вызываются только из `handlers._perform_plan` после `plan_confirm`.
2. **Двухшаговый деструктив.** Даже после плана удаление идёт через явное подтверждение; само
   исполнение делает скрипт, а не ИИ.
3. **Доступ по `ALLOWED_USER_IDS`** и проверка владельца операции в callback.
4. **Лимит шагов** (`AGENT_MAX_STEPS`) не даёт агенту бесконечно крутиться.
5. **Валидация аргументов** инструментов (даты, RRULE, ref) — модель не может протолкнуть мусор в план.
6. **Не выдумывать события** — промпт требует сначала `list_events`; read-only слой не даёт модели
   писать в календарь, даже если бы она «захотела».

## 10. Пример сквозного сценария

Пользователь: «Удали ближайшее вычесывание бобров» (сегодня пятница 07.08, серия по Пн,
10.08 — перенесённое одноразовое в 17:00).

1. `handlers.on_message` → `run_agent`.
2. Шаг 1: модель зовёт `list_events()` (без дат) → каталог:
   ```
   [e1] Вычесывание бобров · Пн, 10 августа, 17:00–18:00
   [e2] Вычесывание бобров · Пн, 17 августа, 16:00–17:00 · каждый Пн
   ```
   `session["refs"]` = {e1: EventData(10.08), e2: EventData(серия)}.
3. Шаг 2: модель выбирает ближайшее и зовёт `propose_delete(ref="e1", scope="instance")`
   → план: [delete: 10.08 17:00, instance].
4. Шаг 3: модель возвращает финальный текст «Запланировал удаление ближайшего…».
5. `handlers` регистрирует `PlanOp`, шлёт текст + «📋 План действий … 1. 🗑 Удалить …» + кнопки.
6. Пользователь жмёт «✅ Выполнить всё» → `_perform_plan` → `exclude_occurrence(e1)`
   (для 10.08 это отдельное одноразовое событие, поэтому фактически `delete_event` по ресурсу)
   → сообщение «✅ Удалено: «Вычесывание бобров»».

Мульти-пример «Перенеси Юайти олпрактика на 19:00 и создай встречу с Аней в 20:00»:
модель за один проход зовёт `propose_update(ref=…, scope=instance)` + `propose_create(…)`,
в план попадают два действия, показываются одной кнопкой и исполняются последовательно.

## 11. Известные ограничения

- Сессии и операции — in-memory: перезапуск бота теряет диалог и ожидающие подтверждения.
- Провайдер LLM обязан поддерживать function calling (tools); у части локальных vLLM-инсталляций
  поддержка неполная.
- Одно пользовательское сообщение обрабатывается синхронно в потоке; при большом каталоге
  (много событий в 90 днях) история растёт — ограничивается `AGENT_CATALOG_LIMIT` и `AGENT_HISTORY_LIMIT`.
- «Ближайшее» определяется относительно `LIST_DEFAULT_DAYS`-окна: события дальше окна модель не видит.
