# AI-CalDav-Bot — как устроен проект

Телеграм-бот для управления Яндекс-календарём (CalDAV) через естественный язык.
Вместо классической схемы «распарсил команду → выполнил» здесь используется
**агентная архитектура**: языковая модель работает как агент с инструментами
(function calling) и сама решает, какие действия предложить, но никогда не пишет
в календарь напрямую.

```
┌────────────┐  сообщение   ┌─────────────────────────────┐
│  Telegram   │ ───────────► │ handlers.on_message          │
│  (aiogram)  │ ◄─────────── │  (aiogram Router)            │
└────────────┘  ответ/кнопка └──────────────┬──────────────┘
                                            │ run_agent(chat_id, text)   (в отдельном потоке)
                                            ▼
                                   ┌────────────────────┐
                                   │ agent.CalendarAgent │   ← LLM с tools
                                   │  · чат-цикл          │
                                   │  · сессии + refs     │
                                   └─────────┬──────────┘
                        read-only (get_period) / staged (reg_list) │ пауза (ask_user) → done
                                             ▼
                                    ┌────────────────────┐
                                    │  AgentResult       │
                                    │  kind: done/ask/   │
                                    │  error · text ·    │
                                    │  plan · questions  │
                                    └─────────┬──────────┘
                                 kind="done" и план непуст:
                                             ▼
                                    PlanOp → кнопка «✅ Выполнить всё / ❌ Отмена»
                                             ▼
                                    handlers._perform_plan → caldav_service (скрипт, не ИИ)
```

Ключевой принцип безопасности повторяется в нескольких местах кода и в промпте:
**LLM планирует, скрипт исполняет**. У нейросети нет доступа к записи в календарь —
только к чтению и к «черновику» плана, который подтверждает человек кнопкой.

## 1. Компоненты

| Файл | Роль |
|---|---|
| `main.py` | Точка входа: создаёт `Bot`/`Dispatcher` aiogram, проверяет подключение к CalDAV, запускает polling. |
| `handlers.py` | Telegram-I/O: принимает текст, запускает агента, показывает план с кнопкой, исполняет план после подтверждения. |
| `agent.py` | **Агент**: 4 инструмента (`get_period`/`reg_list`/`ask_user`/`done`), чат-цикл, сессии, исполнение read-only инструментов. |
| `confirmation.py` | `PlanAction` / `PlanOp`, реестр «ожидающих операций» (TTL 15 мин), клавиатура подтверждения. |
| `asks.py` | Реестр «ожидающих вопросов» `AskQ` (TTL 15 мин) + inline-кнопки вариантов ответа. |
| `caldav_service.py` | CRUD поверх CalDAV: чтение с раскрытием повторов, создание, удаление, `EXDATE`, изменение. |
| `formatting.py` | Рендер: каталог для модели (`format_catalog_compact`), план для человека (`format_plan`), даты и RRULE по-русски. |
| `config.py` | Все настройки из `.env`. |
| `agent_demo.py` | CLI-песочница: гоняем агента без Telegram. |
| `check_connection.py` | CLI-проверка доступа к Яндексу. |

Зависимости: `aiogram` (бот), `caldav` + `icalendar` (протокол и iCal), `recurring-ical-events`
(раскрытие повторов), `openai` SDK (LLM), `python-dotenv` (конфиг). Подробнее — `requirements.txt`.

## 2. Жизненный цикл сообщения (пошагово)

1. Пользователь пишет фразу в Telegram.
2. `handlers.on_message` (`handlers.py:107`):
   - проверяет доступ (`ALLOWED_USER_IDS`);
   - чистит протухшие операции (`cleanup_expired`);
   - шлёт индикатор «печатает» (`ChatAction.TYPING`);
   - **отменяет предыдущий незакрытый план** для этого чата (`_cancel_pending_plan`);
   - вызывает `run_agent(chat_id, text)` в отдельном потоке (`asyncio.to_thread`), чтобы не блокировать
     event loop aiogram.
3. Агент (`agent.run`/`agent.resume`) крутит чат-цикл: зовёт LLM, выполняет `get_period`,
   регистрирует изменения через `reg_list`, ставит на паузу на `ask_user` и завершается `done`.
4. `run_agent` возвращает `AgentResult{kind, text, plan, questions}`.
5. **`kind == "done"`**: если план непуст — создаётся `PlanOp`, в сообщение кладётся
   `format_plan(plan)` + кнопка «✅ Выполнить всё / ❌ Отмена»; текст агента идёт выше списка действий.
   Если план пуст — просто отправляется `result.text` (список событий, «Удалять нечего» и т.п.).
6. **`kind == "ask"`**: каждый вопрос (`result.questions`) уходит отдельным сообщением
   `❓ …` с inline-кнопками вариантов. Подтверждения плана нет — цикл ждёт ответов.
7. Ответ на вопрос (кнопка или текст) возвращается модели как результат инструмента; когда отвечены
   **все** вопросы раунда — цикл возобновляется (`resume_agent`) и приходит к `done`.
8. По кнопке плана:
   - «✅ Выполнить всё» → `handlers._perform_plan` исполняет каждое действие через `caldav_service`
     и заменяет сообщение списком результатов. Результат также дописывается в историю агента
     (`append_assistant_text`), чтобы следующий ход диалога «знал» о сделанном.
   - «❌ Отмена» → «Отменено», операция удаляется из реестра.
9. **`kind == "error"`**: модель не завершила ход (`done`) или исчерпан лимит шагов —
   пользователю отправляется текст ошибки, план отбрасывается.

## 3. Агент (`agent.py`) — самое важное

### 3.1 Идея

Парадигма **«всё есть инструмент»**: агент не отвечает «просто текстом» — каждый ход модели
обязан закончиться вызовом `done` (финальный ответ) или `ask_user` (уточняющий вопрос).
Четыре инструмента покрывают всю поверхность взаимодействия: чтение (`get_period`),
планирование изменений (`reg_list`), вопросы (`ask_user`), завершение (`done`).

Модель видит:
- системный промпт с текущей датой/временем/таймзоной;
- историю диалога (роли `user`/`assistant`/`tool`);
- объявления инструментов (`TOOLS`, генерируются из `build_tools()`).

Скрипт исполняет инструменты и подкладывает результаты обратно в историю как сообщения роли `tool`,
после чего зовёт модель ещё раз — до терминального `done`/`ask_user`.

### 3.2 Инструменты (`TOOLS`, `agent.py:29`)

Всего четыре функции:

| Инструмент | Контроль | Что делает |
|---|---|---|
| `get_period(date_from?, date_to?)` | **read-only, исполняется сразу** | Все события периода, сгруппированы по дням, каталог `[e1] …`. |
| `reg_list(actions)` | staged | Один вызов регистрирует список действий `{op: add\|delete\|update}` в план сессии. |
| `ask_user(question, options)` | **пауза** | Вопрос уходит в чат с кнопками вариантов; ответ возвращается модели как результат инструмента. |
| `done(message)` | **терминальный** | Завершает ход: финальный текст + накопленный план. |

Почему `reg_list`, а не `create_*`: инструмент **не пишет в календарь**. Он лишь валидирует
аргументы и добавляет `PlanAction` в `session["plan"]`. Финальное слово — за кнопкой.
`ask_user` не блокирует пачку: он только регистрирует «ожидающий вопрос», а пауза наступает
после обработки всей пачки.

### 3.3 `get_period` — как агент «видит» календарь

При вызове (`_tool_get_period`):
1. `_resolve_period` определяет окно:
   - есть `date_from` → день начала; если есть `date_to` → до конца этого дня (включительно);
   - только `date_to` → этот день;
   - ничего → **сегодня + `LIST_DEFAULT_DAYS`** (по умолчанию 90 дней).
2. `caldav_service.list_events(start, end)` читает календарь и **раскрывает повторяющиеся серии**
   в отдельные вхождения через `recurring_ical_events` (исключения `EXDATE` уже применены).
3. `format_catalog_compact` свёртывает серию обратно в **одну строку**: `[eN] Название · 16:00–17:00 ·
   каждый Пн · кроме Пн, 10 августа`. Модель не тонет в десятках строк одного повтора, но видит
   паттерн и исключения периода.
4. Одиночные события группируются **по дням**; все строки нумеруются токенами `[e1]…[eN]`
   (уникальны на весь период). Возвращается текст + словарь `{ref: EventData | list[EventData]}`
   (серия → список вхождений периода).
5. Словарь refs кладётся в **сессию** (`session["refs"]`), чтобы последующие сообщения диалога могли
   ссылаться на те же токены.

Пример возврата инструмента:

```
Серии:
  [e1] Занятие математика · 16:00–17:00 · каждый Пн
  [e2] Вычесывание бобров · 16:00–17:00 · каждый Пн · кроме Пн, 10 августа

Одиночные события:
Сб, 8 августа:
  [e3] прогулка с Катей · Сб, 8 августа, 13:00–14:00
Пн, 10 августа:
  [e4] Вычесывание бобров · Пн, 10 августа, 17:00–18:00
```

Если событий нет — возвращается строка `«Ничего не найдено в выбранном периоде.»`, и промпт
требует ответить «Удалять нечего» / «Событий нет», ничего не выдумывая.

### 3.4 Чат-цикл (`CalendarAgent.run`/`_loop`/`resume`)

```
run(chat_id, user_text):
  _prune()                       # убрать сессии, старше AGENT_SESSION_TTL_MIN
  если есть неотвеченные вопросы:
      user_text = ответ на ПЕРВЫЙ неотвеченный вопрос (роль tool)
      если остались другие неотвеченные — return kind="ask" (ждать)
      else — _loop(chat_id)
  иначе:
      история += {"role":"user","content": user_text}
      _loop(chat_id)

_loop(chat_id):                  # до AGENT_MAX_STEPS итераций
  ответ = LLM(messages, tools=TOOLS, tool_choice="auto", temperature=0)
  если tool_calls нет:
      # строгий done: текст без инструментов недопустим
      return kind="error" «агент не вызвал done»
  история += assistant-сообщение с tool_calls
  для каждого tool_call ПО ПОРЯДКУ:
      get_period/reg_list → исполнить, результат роли tool сразу
      ask_user            → зарегистрировать «ожидающий вопрос» (ответа пока нет)
      done                → запомнить message, ответить "Принято." (роль tool)
  если в пачке был ask_user:
      if был и done → done игнорируется (пауза приоритетнее)
      вернуть kind="ask" с новыми вопросами для постинга
  если был done:
      план = session["plan"]; session["plan"] = []
      вернуть kind="done" (текст + план)
лимит шагов без done → kind="error"

resume(chat_id):                 # после ответов на ВСЕ вопросы раунда
  если есть неотвеченные — kind="ask"
  иначе — session["pending_asks"] = [], _loop(chat_id)
```

Особенности:
- `tool_choice="auto"` — модель сама решает, звать ли инструмент; `temperature=0` — детерминированность.
- Каждый виток LLM отправляет **всю историю сессии** (+ свежий system-промпт), поэтому модель
  помнит предыдущие сообщения, каталоги и ответы на вопросы.
- `ask_user` и `done` могут встретиться в одной пачке с другими инструментами: обычные исполняются,
  ask_user паузит (done в той же пачке игнорируется), чтобы не было «вопрос и план одновременно».
- Лимит шагов защищает от зацикливания (например, когда модель раз за разом шлёт неверный `ref`).
- Ошибка LLM оборачивается в `AgentError` и уходит пользователю как «😕 Ошибка агента: …».

### 3.5 Сессии и refs

- Сессия — `dict` в памяти: `{chat_id: {"messages", "refs", "plan", "pending_asks", "ts"}}`.
- Хранится в `CalendarAgent._sessions`, закрыта `threading.RLock`.
- TTL — `AGENT_SESSION_TTL_MIN` (по умолчанию 30 мин), чистка при каждом вызове `run`/`resume`.
- История обрезается до `AGENT_HISTORY_LIMIT` (по умолчанию 30) последних сообщений.
- `refs` живут в сессии специально: модель на следующем сообщении может сослаться на `[e1]` из
  предыдущего каталога, не перечитывая календарь.
- `plan` накапливается через `reg_list` и **переживает паузу на `ask_user`**: действия,
  зарегистрированные до вопроса, попадают в финальный `done`. После `done` план очищается.
- `pending_asks` — ожидающие вопросы раунда (`ask_id`, `tool_call_id`, `question`, `options`,
  `posted`, `answered`); обнуляется при возобновлении цикла.
- Сессии in-memory: после рестарта бота диалог обнуляется.

### 3.6 Системный промпт (`SYSTEM_TEMPLATE`, `agent.py:125`)

Промпт собирается каждый вызов через `build_system_prompt()` и подставляет
`Сегодня / Сейчас / Часовой пояс / LIST_DEFAULT_DAYS`. Правила (в сокращении):
1. Каждый ход обязан закончиться `done` или `ask_user`; обычный текст без инструментов недопустим.
2. Никогда не выдумывать события — сначала `get_period`.
3. «Ближайшее/следующее» → `get_period` без дат (90 дней) и выбор ближайшей даты.
4. Пустой результат → «Удалять нечего», без выдумок.
5. Несколько кандидатов → выбрать очевидное или `ask_user` с вариантами.
6. Одноразовое событие и серия с тем же названием — **разные** события; «все повторения» = только серия.
7. Не планировать несколько действий за ход, если пользователь не просил; все изменения — одним `reg_list`.
8. Повторяющиеся: `instance` = одно вхождение, `all` = вся серия; при неясности — спросить или `instance`.
9. Изменения — только через `reg_list`; до подтверждения писать «сделано/удалено» нельзя.
10. Создание: обязательны `summary` и `start`; повторы через RRULE; для недельного повтора день недели
    `start` обязан совпадать с `BYDAY`.
11. Перенос не меняет длительность, если не просили.
12. `ask_user`: `options` — 1–4 варианта кнопками; после ответа продолжить и завершить `done`.
13. Отвечать кратко по-русски, без markdown/эмодзи, без упоминания `ref`.

### 3.7 Валидация в `reg_list`

Инструмент проверяет аргументы, прежде чем положить действие в план (`_build_add`/`_build_delete`/
`_build_update`); ошибка конкретного действия не роняет остальные:
- `add`: наличие `summary`/`start`, парсинг даты, `duration ≥ 1`, валидация RRULE
  (`vRecur.from_ical` после нормализации). Итог — словарь `payload`.
- `delete`: `ref` обязан существовать в `session["refs"]` (иначе ошибка с подсказкой
  «вызови get_period заново»), `scope` приводится к `instance`/`all`.
- `update`: тот же `ref`-чек, `changes` непустые и содержат хотя бы одно из
  `summary/start/shift_minutes/duration/location`, строки подчищаются.

Каждое действие получает номер («1. ✅ создать «…»») — модель видит, что именно запланировано.

### 3.8 `ask_user` — пауза с кнопками

- `ask_user(question, options)` регистрирует «ожидающий вопрос» (в `asks.py` — реестр `AskQ`
  с TTL 15 минут и inline-клавиатурой `kb_ask`).
- После пачки цикл возвращает `kind="ask"`; `handlers` постит каждый вопрос отдельным сообщением
  `❓ …` с кнопками вариантов (`callback ask:<ask_id>:<i>`).
- **Кнопка** → `agent.answer_ask(...)`: ответ уходит модели как результат инструмента.
- **Текст** вместо кнопки → становится ответом на первый неотвеченный вопрос (как новый ход
  диалога не трактуется).
- Когда отвечены **все** вопросы раунда → `resume_agent` продолжает цикл; модель видит ответы
  и идёт к `done`. Неотвеченные вопросы не перепостятся (флаг `posted`).

### 3.9 Debug-логирование

На уровне `DEBUG` (`logger = logging.getLogger(__name__)`) агент печатает:
```
AGENT chat=777003 шаг=1 вызов LLM (история=3 сообщений)
AGENT chat=777003 шаг=1 tool=get_period args={}
AGENT chat=777003 шаг=1 tool=get_period result='Сб, 8 августа:\n  [e1] прогулка с Катей · …'
AGENT chat=777003 шаг=2 tool_calls=1
AGENT chat=777003 шаг=2 tool=ask_user args={"question":"...","options":[...]}
AGENT chat=777003 шаг=2 пауза: вопросов=1
AGENT chat=777003 ответ на вопрос abc123: 'только это'
```

Это удобно при отладке: видно каждый шаг цикла, аргументы, результаты инструментов и паузы.

## 4. Подтверждение и исполнение плана

### 4.1 `confirmation.py`

- `PlanAction` — одно действие плана: `kind` (`create`/`delete`/`update`), `event` (для delete/update —
  это `EventData` из refs, с `url` и `instance_start`), `payload` (для create), `scope`
  (`instance`/`all`/`single`), `changes` (для update).
- `PlanOp` — `{user_id, actions}`.
- Реестр `PENDING: dict[op_id, BaseOp]` + `_CREATED_AT`. Время жизни операции — `OP_TTL_SECONDS = 900`
  (15 минут), чистка `cleanup_expired()`.
- `register/get/consume` — создать, получить, забрать (и удалить) операцию.
- `kb_plan_confirm(op_id)` — инлайн-кнопки `✅ Выполнить всё` / `❌ Отмена`, callback `op:<id>:plan_confirm`.

### 4.2 Callback (`handlers.on_callback`, `handlers.py:138`)

- Парсится `op:<id>:<action>`.
- Операция обязана существовать и принадлежать тому же пользователю (`cb.from_user.id == op.user_id`).
- `cancel` → сообщение «❌ Отменено».
- `plan_confirm` → `consume` операцию, `_perform_plan` в потоке, сообщение заменяется результатами,
  результат дописывается в историю агента.

### 4.3 Исполнение (`handlers.py:179`)

`_perform_plan` проходит по `op.actions` и вызывает `_perform_action`. Любое `CalDAVError`
не роняет остальные действия — ошибка просто попадает отдельной строкой в результат.

- **create** → `create_event(**payload)` → «✅ Создано: «Название» (…, ЧЧ:ММ) 🔁 каждый Пн».
- **delete**:
  - `scope == "all"` или событие не повторяется → `delete_event(ev)` (удаление ресурса);
  - иначе → `exclude_occurrence(ev)` (добавление `EXDATE` — исключение одного вхождения).
- **update**:
  - повторяющееся и `scope == "instance"` → сначала `exclude_occurrence(ev)`, затем `create_event`
    нового отдельного (неповторяющегося) события с изменёнными полями — классическая техника
    «отменить вхождение в серии + создать копию»;
  - иначе → `update_event(ev, changes)` (правка мастера-события).

`_build_updated_payload` вычисляет новые поля из старых: `start` через `_new_start`
(приоритет `start`, иначе `shift_minutes`), длительность сохраняется, если не задана.

## 5. CalDAV-слой (`caldav_service.py`)

- `CalDAVClient` — ленивый одиночка (модульный фасад `get_client`), `threading.RLock` на все запросы.
  Дискавери: `_find_principal` / `_find_calendar` (прямой `CALENDAR_PATH`, либо выбор по `CALENDAR_ID`,
  либо первый не-«Корзина»).
- `list_events(start, end)` — `calendar.events()` → для каждого мастера `_expand`:
  `recurring_ical_events.of(cal).between(start, end)` раскрывает серии во вхождения
  (с учётом `EXDATE`/`RDATE`). Поле `is_recurring` берётся из наличия `RRULE`, в `EventData.exdates`
  кладутся локальные даты `EXDATE` мастера (для рендера «кроме …»).
- Группировка вхождений по `url` мастера для компактного каталога выполняется в `format_catalog_compact`
  (`formatting.py`): серия → список вхождений периода в `refs`.
- `create_event(summary, start, duration, location, description, rrule)` — собирает `icalendar.VEVENT`
  с `uuid4`-UID, `DTSTART/DTEND` в UTC, `RRULE` через `vRecur`, сохраняет `calendar.save_event`.
- `delete_event(ev)` — `event_by_url(ev.url).delete()` (весь ресурс).
- `exclude_occurrence(ev)` — перезагружает мастер по URL, добавляет `EXDATE`
  (дата для all-day, `datetime` в UTC для обычных), сохраняет.
- `update_event(ev, changes)` — правит `SUMMARY/LOCATION/DTSTART/DTEND` мастера
  (`start` из ISO, либо `shift_minutes`), при смене времени пересчитывает `DTEND` от новой даты.

Тонкость про «перенести 10 августа на час позже»: агент регистрирует `update` (scope=instance) через
`reg_list` → скрипт исключает 10.08 из серии (`EXDATE`) и создаёт одноразовое событие на 10.08 в новое время.
скрипт исключает 10.08 из серии (`EXDATE`) и создаёт одноразовое событие на 10.08 в новое время.
Именно поэтому в календаре появляются две записи: серия без 10.08 + отдельное событие.

## 6. Форматирование (`formatting.py`)

Два разных рендера — для машины и для человека:

- `format_catalog_compact(events, start, end, oneoff_limit) -> (text, refs)` — каталог для LLM:
  серии одной строкой (`«каждый Пн, 16:00–17:00, кроме …»`), одиночные — по дням:
  `«Пн, 10 августа:\n  [eN] описание»`. Описание через `describe_event` — без HTML и эмодзи.
  `refs`: серия → список вхождений, одиночное → `EventData`.
- `format_ask(question)` — текст вопроса `ask_user` (`❓ …`).
- `format_plan(actions)` — красивый список для Telegram (HTML): 
  ```
  📋 План действий
  1. 🗑 Удалить «Вычесывание бобров» (Пн, 10 августа, 17:00)
  2. ✨ Создать «Встреча с Аней» — Пн, 10 августа, 20:00–21:00
  ```
- Вспомогательное: `fmt_date`/`fmt_dtime` (русские даты, «сегодня»/«завтра»), `describe_rrule`
  (RRULE → «каждый Пн»), `_new_start` (вычисление новой даты начала из `changes`).

## 8. Безопасность

1. **Запись только по кнопке.** Ни одна `reg_list`-ветка не вызывает `create_event/delete_event/update_event`;
   они вызываются только из `handlers._perform_plan` после `plan_confirm`.
2. **Двухшаговый деструктив.** Даже после плана удаление идёт через явное подтверждение; само
   исполнение делает скрипт, а не ИИ.
3. **Доступ по `ALLOWED_USER_IDS`** и проверка владельца операции в callback.
4. **Лимит шагов** (`AGENT_MAX_STEPS`) не даёт агенту бесконечно крутиться.
5. **Валидация аргументов** инструментов (даты, RRULE, ref) — модель не может протолкнуть мусор в план.
6. **Не выдумывать события** — промпт требует сначала `get_period`; read-only слой не даёт модели
   писать в календарь, даже если бы она «захотела».
7. **Строгий `done`** — ход без терминального `done`/`ask_user` отбрасывается как ошибка; план
   регистрируется только после явного завершения.

## 10. Пример сквозного сценария

Пользователь: «Удали ближайшее вычесывание бобров» (сегодня пятница 07.08, серия по Пн,
10.08 — перенесённое одноразовое в 17:00).

1. `handlers.on_message` → `run_agent`.
2. Шаг 1: модель зовёт `get_period()` (без дат) → каталог по дням:
   ```
   Пн, 10 августа:
     [e1] Вычесывание бобров · Пн, 10 августа, 17:00–18:00
   Пн, 17 августа:
     [e2] Вычесывание бобров · Пн, 17 августа, 16:00–17:00 · каждый Пн
   ```
   `session["refs"]` = {e1: EventData(10.08), e2: EventData(серия)}.
3. Шаг 2: модель выбирает ближайшее и вызывает `ask_user` с вариантами («только это» / «всю серию»)
   → цикл ставится на паузу, вопрос уходит в чат с кнопками.
4. Пользователь жмёт «только это» → ответ возвращается модели как результат инструмента,
   цикл возобновляется.
5. Шаг 3: модель зовёт `reg_list(actions=[{op:"delete", ref:"e1", scope:"instance"}])` → план
   сессии = [delete: 10.08 17:00, instance].
6. Шаг 4: модель зовёт `done(message="Запланировал удаление ближайшего…")` → `kind="done"`,
   план фиксируется, `session["plan"]` очищается.
7. `handlers` регистрирует `PlanOp`, шлёт текст + «📋 План действий … 1. 🗑 Удалить …» + кнопки.
8. Пользователь жмёт «✅ Выполнить всё» → `_perform_plan` → `exclude_occurrence(e1)`
   (для 10.08 это отдельное одноразовое событие, поэтому фактически `delete_event` по ресурсу)
   → сообщение «✅ Удалено: «Вычесывание бобров»».

Мульти-пример «Перенеси Юайти олпрактика на 19:00 и создай встречу с Аней в 20:00»:
модель за один проход зовёт `reg_list(actions=[{op:"update",…}, {op:"add",…}])`,
в план попадают два действия, показываются одной кнопкой и исполняются последовательно.

## 11. Известные ограничения

- Сессии и операции — in-memory: перезапуск бота теряет диалог и ожидающие подтверждения.
- Провайдер LLM обязан поддерживать function calling (tools); у части локальных vLLM-инсталляций
  поддержка неполная.
- Одно пользовательское сообщение обрабатывается синхронно в потоке; при большом каталоге
  (много событий в 90 днях) история растёт — ограничивается `AGENT_CATALOG_LIMIT` и `AGENT_HISTORY_LIMIT`.
- «Ближайшее» определяется относительно `LIST_DEFAULT_DAYS`-окна: события дальше окна модель не видит.
